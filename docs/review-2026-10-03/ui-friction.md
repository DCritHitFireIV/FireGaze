## Findings（按主任务流逐步骤）

### 步骤 1 找插件（帧 1 工具条 + 列表行）

**P2-1 「有改动待写入」的行在「待应用」筛选下消失；计数与筛选口径互相打架** — 步骤 1（也是步骤 2/8 的落点）
- 位置：帧 1 工具条 `状态 ▾ = 待应用` + AetherDraw 行徽标 `已汉化 252 条 · 有改动待写入` + 右端计数 `… · 待处理 7`。
- 证据：`MatchesFilter` 的 `RowFilter.Pending => info is { HasPack: true, Translated: > 0 } && info.Patch != UITextPatchStatus.Applied`（`UITextTab.cs:526`）；而 `PackNewerThanPatch` 行的 `Patch == Applied`（`DescribeState` `UITextTab.cs:1579`），只落入 `RowFilter.Done`（`:527`）。`NeedsAttention` 却把 `r.PackNewerThanPatch` 计入「待处理」（`:544`）。
- 影响：用户用「待应用」找「还差写盘」的插件时，唯一显示「写入并重载」的那种行被滤掉；同时计数说还有 N 个待处理，无法定位 —— 筛选看起来像坏了。
- 最小修法：`Pending` 分支加 `|| info.PackNewerThanPatch`；或新增下拉项「有改动待写入」。

**P2-2 三套词表：徽标词 / 筛选项 / 计数词互不对应；`失败` 筛选会混入任何「上一次操作失败」的行** — 步骤 1
- 位置：帧 1 工具条 `状态` 下拉、各行 meta 行徽标、计数串。
- 证据：`filterLabels = { "全部", "未汉化", "待应用", "已汉化", "失败", "中文插件" }`（`UITextTab.cs:265`）；徽标实际输出 `有改动待写入` / `需要重打` / `已翻译 N 条 · 未应用` / `上次失败 · 已翻译 N 条` / `翻译中 N / M 条`（`DescribeState` `:1557-1600`）；计数用第三个词 `待处理`（`:346`）。另有 `RowFilter.Failed` 把「note 是 Bad」也算失败（`:528`），于是**上传失败 / 打开失败 / 还原失败**的行会出现在「失败」筛选里，而它的徽标可能是绿色的「已汉化 N 条」（Bad note 不自动过期）。
- 影响：下拉是阅读题（用户得先猜「待应用」等不等于橙色那串字），且「失败」筛选会给出看起来没失败的行 → 信任成本。
- 最小修法：下拉词表改成与徽标同词（`未汉化 / 待写入 / 已汉化 / 失败 / 中文插件`），`失败` 筛选项限定 `Patch == Failed`，行提示失败不进这个筛选；计数项做成可点 = 切到对应筛选。

**P3-1 搜索框占位符写的范围和真实范围不符** — 步骤 1
- `ImGui.InputTextWithHint("###UITextPluginSearch", "搜索插件名…", …)`（`:255`），实际同时匹配 `DisplayName` 与 `InternalName`（`:437-440`，范围只写在 tooltip 里）。
- 建议：占位符改「搜索插件名 / 目录名…」。

**P3-2 筛选后没有「当前 N 行」读数** — 步骤 1，与成熟模块的差异
- 「仓库体检」有 `结果 88 行 · 已选 87` 摘要条；本页改筛选后只剩列表本身，计数仍显示全量 `已装 194 · 已汉化 96 · 待处理 7`，空结果只有一行 `当前筛选下没有插件。`（`:452-456`）。
- 建议：空状态与计数互斥显示，或在计数位置加 `筛选后 N 行`。

**P3-3 筛选下拉的 tooltip 与选项对不上** — 步骤 1
- tooltip `按汉化状态筛选：未汉化 / 已翻译还没写入 / 已汉化 / 上次失败。`（`:271`）用了另外一组词，且漏了 `中文插件`。
- 建议：tooltip 直接复用下拉词表。

### 步骤 2 一键汉化（帧 1 主按钮 + 首次运行弹窗）

**P2-3 终态行的第一个槽位仍叫「一键汉化」，但它是空操作** — 步骤 2（重度用户最常点的那一格）
- 位置：帧 1 AutoHook 行 / 帧 2 同一行：`[一键汉化](白底) [打开](主色) [还原原文] [一键上传]`。
- 证据：`label = retryable ? "重试" : writeOnly ? "写入并重载" : "一键汉化"`（`:734`）——`fullyLocalized` 只影响配色不影响名字；实际点击后走 `targets.Count == 0 && … Patch == Applied` 分支，只写一条 note：`已是最新：没有要翻的条目，补丁也还在。`（`:1798-1806`）。这个过程没有取消（`CanCancel` 到翻译阶段才置 true，`:1820`），要重读一遍 DLL。
- 影响：这与本页自定的命名原则（代码注释 `:711-714`「按钮名跟着这一步真正会做什么走」）矛盾；用户会以为没生效而反复点。
- 最小修法：`fullyLocalized` 时把名字换成 `已汉化`/`重新汉化`，或 disable + tooltip `没有要翻的条目；要重翻先改翻译设置`。

**P2-4 长任务没有速率/剩余时间；「取消的实际范围」只在 tooltip 里** — 步骤 3 看进度
- 位置：帧 1 顶部状态条 `正在汉化 AetherBlackbox：翻译 302 / 964 条` + `取消` + 常显小字 `取消只停止翻译：已经翻好的条目会保留。`
- 证据：实现只输出 `翻译 {done} / {targets.Count} 条（{channel.Name}）`（`:1827-1833`），无 elapsed/ETA；会算预计时间的只有开始前的 `FreeEstimate`（`:2371-2386`，「每个词条约 0.8 秒…大约 N 分钟」）。mockup 里那两句常显说明，在实现里是 `ImGui.SetTooltip`（`:411`、`:714`）——**图比实现更清楚**。
- 影响：964 条的翻译是「反复点、看进度」的核心循环，没有「还要多久」会让用户反复回到这一页；「取消会不会丢已翻内容」是决定点不点取消的关键信息，压在 hover 里。
- 最小修法：状态条补 `已用 m:ss · 约剩 N 分钟`；把「取消只停翻译、已翻的保留」从 tooltip 提到按钮右侧常显（一行放不下就放第二行）。

### 步骤 3/4 看进度、失败重试

无独立新增项：失败路径（P2-1 之外）是清楚的，重试语义「沿用当前通道，从没翻完的地方接着翻」写在 tooltip（`:750-760`）。唯一关联项见 P2-2（失败筛选口径）。

### 步骤 5 还原原文（帧 4 左）

**P2-8 破坏性动作在行内没有危险色，与「仓库体检 / 参与翻译」的删除不一致** — 步骤 5（也影响步骤 1 的误点代价）
- 位置：帧 1 各行第 3 槽 `还原原文` 与 `一键上传`/`打开` **同一视觉重量**；帧 4 左弹窗 `还原`（普通按钮）vs `取消`（焦点环）。
- 证据：`ImGui.Button("还原原文")` 无任何 Push 样式（`:770-790`）；对照 `ui-mockup-repoaudit-v2.html` 的 `button.danger{background:#8c2e2e}`（工具条删除）与 `ui-mockup-contribute-history-v2.html` 帧 4 `.btn.danger 删除` + `取消` 默认焦点。
- 公平说明：产品内并不统一 —— 仓库体检的**弹窗内**「确认删除」也是普通按钮（`RepoAuditTab.Actions.cs:379`），所以这条是「一致性」而非回归。
- 建议：行内 + 弹窗都用红系标出「还原」（`UiHelpers` 加 `PushDangerButton`），与同类模块收敛到一条规则。

### 步骤 6 编辑校对

**P1-2 指引指向已被删除的「详情」按钮（死路）** — 步骤 6（由步骤 2 触发，最常见的路径触发）
- 位置：帧 1 任意「已汉化」行，重按「一键汉化」后行内出现 note。
- 证据：note 文案 `已是最新：没有要翻的条目，补丁也还在。想改某条译文，去行尾「详情 → 编辑校对」。`（`UITextTab.cs:1806`）vs 同一文件 `:791` 注释 `// 「详情」按钮已去掉（2026-10-03）：点整行任意处展开收起`。行内已无「详情」，`编辑校对…` 只存在于展开区（`:1229`）。
- 影响：用户按提示在行尾找「详情」，找不到 → 改译文的第一次尝试失败；而这一刻正是「我点了但好像没反应，我想手动改」的高频时刻。
- 最小修法（<5 行）：改成 `点这一行任意处展开 → 点「编辑校对…」`。

**P2-7 展开手势没有可见性，而它是「编辑校对」的唯一入口** — 步骤 6 / 步骤 8
- 位置：帧 1 行右端无任何展开指示；帧 2 caption 自述「点整行展开（没有「详情」按钮）」。
- 证据：`ImGui.Selectable("##row", isOpen, SpanAllColumns|AllowItemOverlap, …)` 无 tooltip（`:578-585`）；`编辑校对…` 全仓只有 `:1229` 一处（`OpenFor` 只从那里调用）；v5 HTML 里 `.chev` 样式已定义但**没有任何行画它**。
- 影响：上传弹窗（`:1053`）与反馈弹窗（`:1995`）都让人「去编辑校对」，但都没说入口；用户得先猜「整行可点」。
- 最小修法：行尾加 `▸/▾`（成本极低），或给行加 tooltip `点这一行展开：统计 / 重新抽取 / 编辑校对 / 云端译文`。

### 步骤 7 一键上传（帧 3）

**P1-1 上传确认框不再说明「去哪 / 公开性」，与本模块自述的设计口径矛盾** — 步骤 7
- 位置：帧 3 左/右弹窗正文与小字。
- 证据：v4 弹窗写 `会成为一个 GitHub 公开 issue，所有玩家都能看到并下载`，v5 改成 `上传到社区公共库，之后其他玩家「一键汉化」时能直接用到`，**「公开性」与「去向」两句话都没了**；而 `StartUpload` 的注释仍写着 `出站内容要有知情与确认（盲评 CF-04/L1）：先把「发什么、去哪、公开性」摊开`（`UITextTab.cs:915` 附近）。实际去向确认是公开 GitHub issue：`ContributeRelay.URL`（Cloudflare Worker）→ 失败回退 `ContributionsStore.RepoURL/issues/new` 并 `Util.OpenLink`（`ContributeSender.cs:37-64`、`ContributeRelay.cs:74`）。
- 影响：一个不可撤回的公开出站动作（982 条译文进公开 issue / 会弹出浏览器），在点「上传 979 条」前界面上看不到；用户同意的是「社区公共库」这个模糊说法。
- 最小修法（纯文案）：小字补 `会提交到公开的 GitHub 仓库 issue（公共库由它托管）；若中继不可用，会自动打开浏览器里的提交页`；按钮文案可写 `上传到公开库（GitHub）`。

**P2-5 弹窗数字与行徽标不一致且不解释（981 → 979）** — 步骤 7
- 位置：帧 3 左首句 `把「AutoHook」已经翻好的 979 条译文…` vs 帧 1/2 的行徽标 `已汉化 981 条` / 展开区 `已翻译 981 条`。
- 证据：`upload.Total` 是**通过本地检测之后**的条数（`StartUpload`→`FilterHealthy`→`uploadable`，`:870-890`），文案却写「已经翻好的 {Total} 条」（`:1019`）。981−2=979 得用户自己做减法（清单里那 2 条就在下面）。
- 最小修法：`这个插件有 981 条译文，其中 2 条没过本地检测；这次上传 979 条。`

**P3-4 检测结果不留痕，取消弹窗后行内没有任何提示** — 步骤 7 → 步骤 1 回看
- `problems.Count > 0` 时只写 `ActivityLog.Warning` 与弹窗（`:906`）；`notes` 仅在 `uploadable == 0` 时写（`:887`）。关掉弹窗后行内仍是绿的「已汉化 981 条」，用户无法复核「刚才是不是全传上去了」。
- 建议：取消/关闭后给该行留一条 note（`上传 979 条，2 条未过检测`）或徽标加 `· 2 条待修`。

**P3-5 弹窗里同一件事说三遍（挤掉本可放清单的空间）** — 步骤 7
- `修好后（或在编辑器里标「不翻」）再点一次「一键上传」。`（`:1046`）+ `不想分享的条目，可以先到「编辑校对」里改写或标「不翻」。`（`:1053`）+ 清单尾部 `…还有 N 条（去「编辑校对」里按原文搜）`（`:1044`）。三句都在说「去编辑校对改/标不翻」。
- 建议：合并成一句，把省下的两行给清单子窗口（现在最多显示 8 行）。

### 步骤 8 展开详情 / 云端下载（帧 2 + 帧 4 右）

**P2-6 「主按钮」/「一键汉化」指向不明，指向的还不是主色按钮** — 步骤 8 → 步骤 2 回路
- 位置：帧 2 AutoHook 展开区 `（本机改过的译文不会被覆盖；下载后点这一行的主按钮写入插件）`；帧 4 右弹窗末句 `应用后还要点这一行的「一键汉化」才会写进插件。`
- 证据：`UITextTab.cs:1346`（主按钮）、`:1455`（一键汉化）、`:1495`（`已应用 {changed} 条，点「一键汉化」重打补丁生效`）。而此时帧面事实是：`[一键汉化]` 是**白底**、`[打开]` 才是**主色**（`DrawRowActions`：`fullyLocalized` 时 `openButton` primary=true、主按钮不 PushPrimary，`:730-745 / 1113-1116`）；而应用云端包之后 `PackNewerThanPatch=true`，该按钮名字会变成 **`写入并重载`**（`:733-734`）——文案点名的两个名字都不是它。
- 影响：这是「下载译文 → 应用 → 写盘」链路的最后一步指引，两处措辞不同且都对不上按钮，用户得靠猜。
- 最小修法：统一成 `点这一行最左边的按钮（此时会显示「写入并重载」）`；或直接在展开区/弹窗里放一个「写入并重载」按钮。

**P3-2 云端包行的「下载 —」与右侧「下载译文」同名异义** — 步骤 8
- `var downloads = pack.Downloads > 0 ? $"下载 {pack.Downloads}" : "下载 —";`（`:1318`）与按钮「下载译文」（`:1327`）并排，前者是**计数**、后者是**动作**，同一个词两种词性。
- 建议：计数写成 `下载数 —` / `0 次下载`。

**P3-6 展开区末句是 SameLine 追在按钮后（推断：窄窗口/多包时会顶出裁剪区）** — 步骤 8

- 建议：这句改成 `ImGui.NewLine()` 或 `TextWrapped`；顺便与 mockup 对齐。

## 与三个成熟模块的一致性

**一致（可迁移的心智模型）**
1. **视觉变量与骨架**：同一套 `--win-bg/--panel/--border/--text/--muted` + `good/warn/bad/info`，同字体栈、同页签/品牌行/分隔线结构（`ui-mockup-uitext-v5-list.html` vs `ui-mockup-contribute-*.html` vs `ui-mockup-repoaudit-v2.html`）。
2. **确认框模式**：先摊开「做什么 / 后果 / 可逆性」+ 默认焦点在「取消」。「插件汉化」是这一模式最完整的实现（4 处确认框 + 免费通道确认），比「仓库体检」的删除确认更规范（后者缺 default focus）。
3. **可逆性叙事**：仓库体检是「备份 + 撤回上次操作 + 打开备份目录」；本页对应「原文件自动备份 + 还原原文（自动重载）」，文案在首行、展开区、弹窗里各说一次，语义一致。

**差异（值得收敛）**
| # | 维度 | 成熟模块 | 插件汉化 | 判断 |
|---|---|---|---|---|
| A | **如何选** | 勾选 + 批量工具条 + `结果 N 行 · 已选 M` 摘要（仓库体检、参与翻译）；操作对象是「所选集合」 | 无勾选、无摘要；每行 4 个按钮，操作对象是「这一行」 | P2-9/P3-2：单插件一键动作更直接，但**同名按钮在 194 行里重复出现**（`一键汉化`×N、`还原原文`×N），误点邻近按钮的代价是写盘 + 重载；且筛选后看不到还剩几行，缺少成熟模块的读数条 |
| B | **如何确认** | 仓库体检删除确认：弹窗 + 样本清单 + `确认删除/取消`（无 default focus）；参与翻译删除确认：`.btn.danger` + 取消 default focus | 5 个弹窗全部 default focus=取消（更好）；但**行内破坏动作无危险色**，弹窗里提交按钮也是普通色 | P2-8：把「提交动作的主色/危险色」定成一条跨页规则（现在产品内有 3 种做法：仓库体检弹窗普通、参与翻译红、本页普通+焦点环） |
| C | **如何撤销** | 仓库体检：`撤回：删除 84 个 · 20:31` 常驻 + UndoHistory 多步；参与翻译：`撤回删除` 常驻 | 只有「还原原文」（整插件粒度，且**没有「撤销上一次汉化」入口**）；单条译文改动靠编辑器/云端包覆盖 | 可讨论：写盘 + 重载之后无法一步回到「刚才那次汉化之前」，重度用户在多插件连点时会缺一个安全网。当前靠备份 + 还原，成本是整插件回退 |
| D | **强调色** | 安装器 / 仓库体检 mockup：`--accent:#ffb35c`（橙）；参与翻译：`#8cbfff`（蓝）+ 主按钮 `#2f4a6d` | 与「参与翻译」同族（蓝 `#8cbfff`、主按钮 `#2f4a6d`），`UiHelpers.PushPrimaryButton` 注释「蓝一点」+ `PushEnableButton` 绿 | P3-7（跨页）：产品内两套强调色并存；本页继承蓝系，但与仓库体检/安装器的橙系无统一规则。建议在 `UiHelpers` 里定一个「跨页主色」，至少要说明哪些页允许橙 |
| E | **状态密度** | 参与翻译：状态列（你译/机器译/缺译）+ 视图切换 + 计数；仓库体检：状态列 + 严重度排序 + 筛选单选组 | 状态徽标在 meta 行行首固定 x（便于竖向扫，好）；但 6 种徽标色 + 主色蓝 + 绿色启用按钮 | P3-5：色板已偏多；`中文插件`（终态、无需操作）用的是最亮的紫 `#c8b4f5` / `Skip=(0.78,0.70,0.95)`，比「需要你动手」的徽标更抢眼。**注意** `UiHelpers.Skip` 注释说明这是 2026-10-02 F8 的有意选择（不复用 Info 蓝）——建议只降明度，不要改回蓝 |
