## 2. 功能分级表
### 分级依据（先说口径）
简介的排序**不能按代码行数排**，否则会把"机构重量"当"用户价值"：体检≈3.2k 行、图标链路≈1.7k 行、安装器增强≈0.6k 行、汉化≈0.5k 行（见每行证据）。我用的五条判据与用户给的一致，但权重按"简介预算"排：
1. **效果出现在谁的地盘**（游戏自己的插件安装器 = 无需打开本插件窗口，权重最高）；

## 3. 简介写作规则
### 三层承载模型（先定容器，再定内容）
| 容器 | 预算 | 承载 |
|---|---|---|
| **市场简介**（`Punchline` / `Description`） | Punchline 1 行；Description **2–3 行** | **只放核心**：每行 = 一个"用户能感知的结果" |
| **README** | 不限 | 完整功能清单（核心 + 支撑 + 次要）、已知问题、边界与免责、命令用法 |
| **页内 tooltip / 灰字 / 状态行** | 不限 | 口径、默认值、机制名、失败时怎么办 |
这条模型直接回答用户那句抱怨：**次要功能不是不能写，是不能写错容器。**
### 简介里应该写什么
1. **结果，不写控件**：写"简介会显示中文"，不写"启用简介汉化复选框"。
2. **每个核心一行**：汉化一行（看到的变了什么）、体检一行（做完得到了什么，含"可批量停用或删除 + 删除前备份可撤回"这条安全承诺，它是核心 ② 的一部分）。
3. **必要时补一行"支撑"并标注启用状态**：若坚持保留"拦住自动刷新"，该行必须以用户语言写结果（"安装器列表不再被后台刷新顶回顶部"），并同时交代默认关闭。
4. **范围词承担边界**：用"第三方"这一个词把范围说清，不用括号解释（当前 `pluginmaster.json:5-6` 已经做到）。
### 简介里绝对不能写（附证据）
1. **页签内的子控件与子数据**：图标检查/补下、"显示插件图标"、图标条、"本库已装"统计、排序方式、"首次记录"、筛选/搜索、"只看有/未安装"。它们都是**核心 ② 页里的零件**（`RepoAuditTab.cs:283/296/320/349/442-446/919`），写进简介就等于把工具条抄进海报。**注**：旧版评审曾建议"README 与市场描述补一句新能力：看清每条库链在本机装了几个插件"（`docs/hci/review-2026-09-17-repoaudit-usage-heuristic.md` AU-10-1）；该建议对 README 成立，对市场简介不成立——用户后来的两次提交（`HEAD:181/183`）把它从简介删掉、方向正确，但它应该在 README 里得到兑现（见 F3）。
2. **机制与实现**：图标落盘缓存目录、注入卫月图标缓存、反射读卫月内部字段、备份里包含 `dalamudConfig.json`（`DalamudRepos.cs:333-338`）、ETag/304、镜像竞速、并发数、"最多再等 4 秒"收尾。这些是 tooltip 与日志的素材（`RepoAuditTab.cs:296-299`、`:365-370`）。
3. **配置细节与默认值**：三个字段各自的默认呈现方式（`Configuration.cs:76-80`）、"扫描范围含已停用"、开关位置。
4. **数字堆砌**：词表条数、"1500+ 条"、并发 8、超时 120 秒。数字会过期，且不回答"我为什么装它"。
5. **技术词**：重载、钩子、清单、注入、缓存失效、验证。跨产物用词统一为游戏里看得见的词（这个词表问题此前已被 `AR-08/AR-09` 记录）。
6. **把默认关的功能写成"已有能力"**：要么不写，要么写"默认关闭，需自己打开"。现有三行简介在 `HEAD:180`（删掉"（默认关闭，可在设置页打开）"）之后不再交代这一点。
7. **用"等"字收尾、用括号塞解释**：这两条是用户自己立过的风格红线（`HEAD:180/181/183` 的提交语就是"按「非必要不用括号」清掉其余括注"、"删掉…一行与…括注"）。
8. **已知问题与免责声明**：放 README（`README.md` 已有免责声明一节），简介不承担这个功能。
