# FireGaze「插件汉化」改版 · 还原图认知摩擦盲评

- 日期：2026-10-01
- 评审对象：`Resources/ui-mockup-uitext-list.png`（4 帧）、`Resources/ui-mockup-uitext-editor.png`（2 帧），并核对对应 HTML 源码文案
- 方法：cognitive-friction-detector（先界定用户 / 任务 / 设计问题 → 分离观测事实与推断 → 逐条摩擦点 + 严重度 → 标注不确定性 → 给下一步）
- 盲评声明：只看还原图与 HTML，不看实现代码。凡判断依赖实机行为的（悬停提示、键盘、滚动、进度动画、弹窗是否真的存在、默认值）一律标注「需实机确认」。

## 用户与任务假设（评审基准）

- **普通用户**：中文玩家，装了上百个插件，想让插件界面变成中文。任务 = 在列表里找到那个插件 → 点一次「一键汉化」→ 等 → 完成。
- **老用户**：已有若干插件汉化过。任务 = 插件更新后重新汉化 / 还原原文 / 改翻译通道。
- **高级用户**：愿意逐条校对。任务 = 进「编辑校对」改几条、标记几条、重新应用。
- **设计问题**：这三类人能不能以最少认知负担走完路径；出错时知不知道下一步做什么；破坏性动作有没有护栏。

**还原图里已经做到、改动时不要退回的地方**（先说好话，避免重构时被削掉）：

1. 一键汉化的进度**画在当时那一行里**，其它行不受影响（帧 3），不弹独立进度窗；
2. 失败态给了**原因 + 后果 + 「已翻好的不会丢」**（帧 4），比只说「失败了」好得多；
3. 无法汉化的插件有**解释型空状态**（带壳/加密 → 读不出文本 → 不会崩），不是静默失败；
4. 「翻译设置」独立成窗、入口在页签工具栏，符合「配置不进翻译流程」的目标；
5. 按钮密度已明显克制：每行最多两个按钮、编辑器工具栏只剩四个。

---

## ① 一句话总评

主线（列表 → 行内「一键汉化」→ 行内进度 → 完成并写明已自动重载）已经比旧版清晰，基本满足「配置搬进设置」「重载不再是独立步骤」「去掉多余按钮」三条目标；但**页签命名与状态术语会让第一次使用的人走错门**，而**取消语义、失败后的恢复路径、还原原文的护栏**这三处关键设计在图上完全没有交代，属于发布前必须补齐的空白。无 P0 级问题。

## ② 逐条摩擦点

### P1

#### F1 ｜ P1 ｜ 页签「简介汉化」与「插件汉化」一字之差

- **用户场景**：用户听说 FireGaze 能「把插件变中文」，打开主窗口看到五个页签：简介汉化 / 仓库体检 / 插件安装器 / 参与翻译 / 插件汉化。他点了第一个「简介汉化」（列表里排最前），看到的是安装器简介的翻译表，找不到「一键汉化」按钮——很可能就此认为功能没做出来或坏了。
- **证据**：帧 1 页签行原文 `简介汉化 仓库体检 插件安装器 参与翻译 插件汉化`；两个页签都含「汉化」，第一个词只差两个字，且「简介」与「插件」在这一屏语境里都不足以区分对象。
- **摩擦类型**：术语歧义 → 导航走错门（注意力与记忆负担）。
- **修改建议**：把新页签按「翻的是什么」命名——用 **「界面汉化」**（对「简介汉化」），或加前限定 **「插件界面汉化」**；同时给两个页签加 tooltip 对照（「安装器里显示的简介文字」 vs 「插件自己窗口里的文字」）。若短期不想改 tab 名，至少在页签行加一行灰字分工说明。允许的话把两个汉化页签排在一起。

#### F2 ｜ P1 ｜ 「取消」的适用边界未定义，写入 DLL 阶段的安全性没有交代

- **用户场景**：用户点了 BOCCHI 的「一键汉化」，进度 137/255。此时他看到行内只有一个「取消」。他点下去：已翻的 137 条还在吗？如果此刻已经进入「写入补丁」甚至「重载插件」，取消会不会写坏插件文件？还是说取消只在翻译阶段有效、按钮会自己消失？图上都没有答案。
- **证据**：帧 3 行内只有 `取消` 一个按钮；步骤行写 `正在翻译（deepseek）… 之后会自动写入补丁并重载插件`——即一次点击背后有三个阶段（翻译 → 写入 → 重载），但取消的边界没画出。恢复图里有写结果的行（帧 4）说明写入结果是真实文件改动，且有备份（展开区「补丁：未应用（原始文件已备份）」）。
- **摩擦类型**：隐藏状态 + 破坏性操作护栏缺失（用户无法预判自己这一下取消的后果）。
- **修改建议**：定义并画进恢复图——① 翻译阶段：`取消` 可点，点击后弹确认，文案明示「已翻好的 N 条会保留，之后可继续」；② 进入写入后：按钮变为禁用或消失，步骤行显示「正在写入补丁，请稍候，此步不能取消」；③ 写入必须是原子操作（临时文件 + 重命名，或已有备份机制），重载阶段不可取消。这条即使实现在代码里已经稳，也必须在图上写明，否则评审与验收都没有依据。

#### F3 ｜ P1（条件）｜ 「零配置即可一键汉化」是目标 2 的前提，但还原图无法证明默认通道

- **用户场景**：新装用户没配过任何东西，点 BOCCHI「一键汉化」（255 条）。如果默认通道是「大模型（自填 key）」而 key 是空的，他会立刻得到一次失败——第一次使用就撞墙，目标「列表上直接点一键汉化就能完成」在首次体验上不成立。
- **证据**：设置窗口帧显示 `大模型（自填 key）` 被选中、key 行写着 `已保存（sk-…4f2a）`——这是一张**已配置状态的图**，不能证明新装默认值。而设置窗的提示语自己写着「条目多时建议用自己的大模型 key」，说明免费通道是允许裸奔的路径。
- **摩擦类型**：默认值风险（推断项，需实机确认）。
- **修改建议**：明确并验证两点——① 新装默认通道 = `免费·自动`；② 未配 key 时「一键汉化」必须能跑通（哪怕会因限流中途失败，也要是「跑了但被限流」而不是「没 key 直接拒绝」）。建议补一张**首次运行帧**（无 key、全列表未汉化、设置入口处有「建议先看看翻译设置」的弱提示）进恢复图，作为验收依据。

### P2

#### F4 ｜ P2（条件升级 P1）｜ 失败恢复只有「去拿一个 key」一条路

- **用户场景**：免费通道被限流，行内提示「到『翻译设置』里换成大模型（自填 key）后重试」。不想折腾 API key 的用户在这里断头——他不知道「等一会儿再点重试也可能成功」。
- **证据**：帧 4 失败行原文 `翻译通道不可用：免费接口被限流（429）。到「翻译设置」里换成大模型（自填 key）后重试，已经翻好的 12 条不会丢。` 行内按钮只有 `重试`；设置窗的提示语证实免费通道是「退避、连续被限就停下」而非永久不可用。
- **摩擦类型**：恢复路径单一 + 技术措辞（`429`）。
- **修改建议**：① 文案拆成两条路——「免费通道暂时被限流，**等几分钟再点重试**可能就好了；想稳定跑大批量，可在翻译设置里填自己的 key」；② 行内补一个 **「打开翻译设置」** 次级按钮，让「去设置」这句话变成一次点击而不是去找工具栏；③ 有条件时显示「预计 X 分钟后可重试」。如果实测发现免费通道在 >100 条规模上**必然失败**（而非偶发），本项升级为 P1。

#### F5 ｜ P2 ｜ 大批量任务没有前瞻提示，失败后才告知

- **用户场景**：用户对 255 条的插件点下「一键汉化」，默认走免费通道。几分钟后中途失败；若事前知道「这个量级免费通道大概率被限流」，他可以选择先换通道或接受分段完成。
- **证据**：帧 3 只有进度与步骤说明，没有任何关于时长或限流风险的提示；相关提示只存在于设置窗提示语里，而普通用户可能从未打开设置窗。
- **摩擦类型**：可预防的失败被推迟暴露。
- **修改建议**：在任务开始时，对「条目数 > 阈值（如 100）+ 免费通道」给一次性的行内弱提示（不是弹窗）：「255 条，免费通道可能要十几分钟，中途可能被限流；可在翻译设置里换成自己的 key」。阈值与文案可配置。

#### F6 ｜ P2 ｜ 「写入补丁 / 重载插件」阶段在图上不存在

- **用户场景**：翻译进度到 255/255 后，行里按完成前的最后一句话应该发生「写入 + 重载」。这段时间插件自己的窗口可能闪一下、关闭重开或状态重置，用户会以为出了事故——而这正是改版目标里强调「自动完成、不展示步骤」的那一步，反而最需要一行归属说明。
- **证据**：帧 3 步骤行只描述「正在翻译…之后会自动写入补丁并重载插件」；帧 4 直接跳到 `一键汉化完成：翻译 255 条 · 写入补丁 255 处 · 插件已重新加载。` 中间状态未画。
- **摩擦类型**：隐藏状态 / 反馈缺失。
- **修改建议**：步骤行升级为阶段指示：`正在翻译 137/255` → `正在写入补丁…（不可取消）` → `正在重载插件…` → `完成`；成功文案保留现在的信息量。同时检查重载期间 FireGaze 自身窗口是否稳定（需实机确认）。

#### F7 ｜ P2（需实机确认）｜ 边翻这一个、边点另一个：并发与排队未定义

- **用户场景**：帧 3 的图上说明写着「可以换别的插件」。用户真的去点了另一行的「一键汉化」——是进入队列、并行跑、还是被静默拒绝？如果被拒绝却没有任何反馈，这是典型的「点了没反应」。
- **证据**：帧 3 其它行保持常态可点外观（SimpleTweaks 行按钮样式不变），没有排队提示、没有禁用态。
- **摩擦类型**：隐藏状态 / 反馈缺失。
- **修改建议**：二选一并画进恢复图——① 排队：其它行主按钮显示「排队（第 2 位）」；② 禁止并发：其它行按钮置灰 + tooltip「正在汉化 BOCCHI…」。另需确认：翻译进行中，该行的「编辑校对」是否也应被限制（避免边翻边改）。

#### F8 ｜ P2 ｜ 「汉化 / 翻译」两套词、三种按钮动词、两种计数单位混用

- **用户场景**：同一屏里，已完成的插件是「已汉化 11 处」，待应用的插件是「已翻译 65 条 · 未应用」，未开始的插件是「未汉化 · 候选 255 条」；按钮分别是「更新汉化 / 应用汉化 / 一键汉化」。用户需要自己在脑子里建立一张对照表：翻译 = 只生成译文，汉化 = 已写入插件；「处」和「条」是同一个东西；「应用汉化」不会帮他翻译那 13 条没翻的。工具栏的「已汉化 12」还和行内「已汉化 11 处」用了同一个词，但单位一个是插件数、一个是字符串数。
- **证据**：帧 1 徽标与按钮原文；帧 4 完成态 `已汉化 255 处`。
- **摩擦类型**：术语系统不统一 → 认知负担与预期错位。
- **修改建议**：① 保留「翻译/汉化」区分但**在每个徽标里把状态说完整**，如 `已翻译 65 条 · 未写入插件`、`已汉化 11 处`、`可翻译 255 条（未开始）`；② 按钮动词收敛：状态放徽标、动作可统一为「一键汉化」的不同后缀或都用「汉化」，如 `一键汉化` / `应用已翻译文` / `检查更新并重打`，并在 tooltip 里各写一句「会做什么」；③ 计数统一用「条」，工具栏改成 `已汉化 12 个插件`。

#### F9 ｜ P2 ｜ 198 行的列表没有按汉化状态筛 / 排

- **用户场景**：用户想「把值得翻的插件先翻了」。他面对 198 行，只能靠逐行读徽标判断，或者记得插件名去搜索。其中大量行会显示「没找到可翻译的界面文本」，进一步稀释注意力。
- **证据**：工具栏只有 `搜索插件名 / 内部名…`、`只看第三方`、`翻译设置…`、`已装 198 · 已汉化 12`。
- **摩擦类型**：信息过载 / 检索成本。
- **修改建议**：加一个状态筛选（全部 / 未汉化 / 已汉化 / 无法汉化）或「只看能汉化的（N）」快捷开关；至少支持按「候选条数」排序，让大插件浮上来。筛选状态要能与搜索叠加。

#### F10 ｜ P2 ｜ 展开区的统计行是一串行话

- **用户场景**：用户对 Orbwalker 点了展开，想弄明白「为什么只翻了 65 条」。他看到的是：`候选 78 条 · 已翻 65 条 · 未翻 13 条 · 灰名单 7 条 · 标记不翻 0 条 ｜ 补丁：未应用（原始文件已备份）`——六个计数、三个术语（候选 / 灰名单 / 标记不翻）、一个状态（补丁未应用），全部是机器视角的字段名。
- **证据**：帧 2 展开区原文；同屏还有一句 `普通用户看这里就够：点上面的「应用汉化」，插件会自动重载，界面立刻变中文。` 说明作者本人也知道这一块「不是给普通用户的」。
- **摩擦类型**：认知负担 / 术语密度。
- **修改建议**：统计区分两层：第一层用一句话讲人话——「这个插件带 78 条界面文本，已翻 65 条；还有 13 条没翻（其中 7 条被判定不安全、默认跳过）」；第二层技术细节（灰名单、标记不翻、补丁状态）缩进为次要样式或放进「编辑校对」页头。判据：展开区的第一句应该能直接回答「我现在该点什么、点了会发生什么」。

#### F11 ｜ P2 ｜ 部分汉化的结果不预告、完成也不说明

- **用户场景**：Orbwalker 是 65/78。用户点「应用汉化」，期待「汉化完成」。实际只写入 65 条、13 条仍是英文；界面不会告诉他差在哪、还能不能补齐。
- **证据**：徽标 `已翻译 65 条 · 未应用` 不显示 78 与 13（要展开才看到）；「应用汉化」按钮无 tooltip；帧 4 只画了整单完成的例子。
- **摩擦类型**：预期错位 / 完成度不透明。
- **修改建议**：① 「应用汉化」tooltip：「将写入已翻好的 65 条（还有 13 条未翻）」；② 完成文案按实际给不完整提示：「已写入 65 处；还有 13 条未翻，可打开『编辑校对』补齐」；③ 徽标加分母写法，如 `已翻译 65 / 78 条`。

#### F12 ｜ P2 ｜ 「还原原文」贴着「更新汉化」，没有确认也没有后果说明

- **用户场景**：老用户想点「更新汉化」，误点到旁边同样大小、同样灰底的「还原原文」——已应用的补丁被撤掉、插件重载、界面回到英文。他慌乱地想：我编辑校对过的译文还在吗？要重来一遍吗？
- **证据**：帧 1 / 4 已汉化行两个按钮 `更新汉化` `还原原文` 并排、样式同级；图中没有任何确认或结果说明；展开区有「原始文件已备份」，说明实现层有备份意识。
- **摩擦类型**：破坏性操作护栏不足（低概率高烦躁）。
- **修改建议**：如果「还原」不影响译文表（只是撤补丁），在按钮 tooltip 与还原后的一行状态里讲明：「已还原原文 · 译文仍保留，可随时重新应用」；在此基础上**建议加二次确认（默认焦点在取消，沿用 FireGaze 既有删除弹窗口径）或提供一次性撤销**。如果还原会丢弃任何用户编辑，则必须二次确认，且文案讲清丢什么、能否恢复。

#### F13 ｜ P2 ｜ 插件更新后「补丁失效 / 自动重打失败」没有状态

- **用户场景**：老用户昨天汉化过的插件今天更新了。设置里勾着「插件更新后自动重打汉化补丁」，但如果重打失败（文件被换、哈希不符、插件锁定），列表却仍显示「已汉化」——用户以为还有中文，进去发现是英文，信任受损。
- **证据**：设置窗有该选项（默认勾选）；列表状态机只画了三种状态（未汉化 / 已翻译未应用 / 已汉化），没有「插件已更新，补丁待重打 / 重打失败」。
- **摩擦类型**：隐藏状态 / 状态说谎。
- **修改建议**：补第四种状态 `插件已更新 · 补丁待重打`（可点击重打）与失败态 `自动重打失败 · 点此重试`；并在工具栏汇总里给一个弱提醒（如「2 个插件的汉化需要重打」）。

#### F14 ｜ P2（需实机确认）｜ 编辑器里「标记不翻」和逐条动作入口不可见

- **用户场景**：高级用户进「编辑校对」想标掉两条不该翻的字符串。编辑器帧里可以看到筛选器里有「不翻」分类，但**没有任何可见入口**说明怎么把一条标记成不翻（右键？双击？图标？）。同样的，逐条「还原这条译文」也不可见。
- **证据**：列表展开区宣称编辑校对支持「逐条改译文、标记『不翻』、重新抽取」；但编辑器帧 1 的表格只有 4 列（状态图标 / 上下文 / 原文 / 译文），工具栏 4 个按钮，均无「不翻」动作。
- **摩擦类型**：可发现性（隐藏功能）。
- **修改建议**：若动作在右键菜单里，请在表头或表格上方加一行操作提示（「右键一行：标记不翻 / 复制原文 / 还原这条」）；更好的做法是行悬停时出现一个小操作入口。若「不翻」只能靠勾选框批量做，也要在图上画出来。此项需实机确认现有交互后再定改法。

#### F15 ｜ P2 ｜ 编辑器筛选模型歧义：候选与已翻 / 未翻并非并列关系

- **用户场景**：用户看到六个单选项：候选 / 灰名单 / 未翻 / 已翻 / 不翻 / 全部。单选按钮的形态暗示这是互斥分区；但实际上「候选 = 已翻 + 未翻」（65 + 13 = 78），它们互相重叠。用户点「候选」和点「全部」的差别是什么？点「已翻」还能不能看到未翻？都不清楚。
- **证据**：帧 1 页头 `候选 78 · 灰名单 7 · 已翻 65 · 不翻 0`，按钮 `批量翻译未翻 (13)`；65 + 13 = 78 可验证重叠关系；且页头计数**漏掉了未翻 13**。
- **摩擦类型**：心智模型不一致 / 过滤语义模糊。
- **修改建议**：① 给每个筛选项带上计数：`未翻 8` 这类写法直接可用（图内数字自洽）；② 把层级讲清：`全部（78）｜未翻（13）｜已翻（65）｜灰名单（7）｜不翻（0）`，去掉「候选」这个与其他项不同层次的词（或改成「可翻译（78）」并注明 = 未翻 + 已翻）；③ 页头计数补齐未翻。

#### F16 ｜ P2 ｜ 表格首列的 ✔ / ⚠ / · 没有图例

- **用户场景**：用户看到「Casters → 法系」前面是 ⚠，而别的行是 ✔。他想知道 ⚠ 是「翻译可能有问题」还是「这一条被标了不翻」还是「格式警告」。
- **证据**：帧 1 表格首列有 ✔（绿）/⚠（黄）/·（灰）三种符号，页面无图例。
- **摩擦类型**：符号无解释 / 需要猜测。
- **修改建议**：表头该列加 title 或在表格上方加一行小图例：`✔ 已翻 · ⚠ 待确认（灰名单/有风险）· 未翻`；悬停该符号给一句具体原因（需实机确认悬停是否可行）。

#### F17 ｜ P2 ｜ 自动保存没有撤销，也没有保存反馈

- **用户场景**：用户改一条较长的译文，手滑失焦；自动保存已经写下去。他想撤销——没有 Ctrl+Z，也没有「已保存 / 撤销」提示。工具栏那句「自动保存」是静态的，不告诉他刚才那一下有没有落盘。
- **证据**：帧 1 工具栏右侧 `通道：deepseek · 自动保存`；表格译文列有虚线（编辑态暗示）；页脚只有「上次操作：已写入 65 处译文并重载插件」——那是应用操作，不是编辑保存。
- **摩擦类型**：反馈缺失 / 不可逆（小幅）。
- **修改建议**：① 编辑保存后给一次短暂的「已保存 15:42:31」状态（可与页脚复用）；② 提供撤销：至少支持 Ctrl+Z 撤销上一次单元格编辑，或行内「还原这条」；③ 明确「自动保存只改本机词表，写进插件要按应用汉化」——避免用户以为改完就生效。

### P3

#### F18 ｜ P3 ｜ 设置窗五个通道并列，地址 / 模型字段对默认项常显

- **用户场景**：普通用户为了一次限流失败打开设置，迎面是 5 个单选项（免费·自动 / Google 免 key / MyMemory / 大模型（自填 key）/ DeepL）加接口地址、模型、key 三行。他的心智里只有两个概念：用免费的，或用我自己的 key。
- **证据**：帧 3（设置窗）原文。
- **摩擦类型**：选择过载 / 配置负担。
- **修改建议**：默认只展示两档——`免费（自动）` 与 `用我自己的 key（大模型）`，其余通道收进「高级通道」折叠区；「接口地址 / 模型」仅在选中「其它 OpenAI 兼容服务」时出现，DeepSeek 官方时隐藏或收进高级。保持底层枚举不变，只改呈现。

#### F19 ｜ P3（需实机确认）｜ key 字段把说明文字当内容、保存 / 清除语义含糊

- **用户场景**：用户想换 key，看到输入框里写着「已保存（sk-…4f2a），要换就粘贴新的」——点进去是清空还是留在后面拼接？按下「保存 key」之前输入框里的字算不算数？「清除」没有确认。
- **证据**：帧 3 key 行原文；旁边还有「保存 key / 清除 / 测试连接」三按钮。
- **摩擦类型**：控件语义模糊。
- **修改建议**：输入框默认留空、placeholder 写「粘贴新 key 即可更换」；已保存状态放框外灰字「已保存 · 尾号 4f2a」；「清除」加二次确认；保存成功后按钮/状态给反馈（需实机确认现有行为）。

#### F20 ｜ P3 ｜ 从编辑器改配置要绕路；「应用汉化」没提自动重载

- **用户场景**：用户在编辑校对窗口里看到 `通道：deepseek`，想换成别的通道——那是一行纯文本，点不了；他得关掉/最小化编辑器，回到列表窗口点「翻译设置…」。
- **证据**：帧 1（编辑器）工具栏右侧文本；列表帧工具栏有 `翻译设置…`。
- **摩擦类型**：跨窗口往返成本。
- **修改建议**：把 `通道：deepseek` 做成可点击链接样式，点击打开翻译设置窗；「应用汉化」按钮加 tooltip「会按设置自动重载插件」，与列表页说法保持一致。

#### F21 ｜ P3 ｜ 面向用户的文案里混入开发者措辞

- **用户场景 / 证据**：`免费接口被限流（429）`；`这个插件的主程序集带壳/加密，读不出界面文本`；`只看第三方`。普通用户不一定知道 429、程序集、带壳是什么，也不一定分得清「第三方」相对谁而言。
- **摩擦类型**：术语门槛。
- **修改建议**：给普通用户层的文案去技术化——「免费翻译接口暂时用不了（被限流），等一会儿再试」/「这个插件做了加密保护，读不出界面文字（不会出错，也不会乱改）」；「只看第三方」改为「只看社区插件」或改为三态筛选（全部 / 官方 / 社区）。技术原词可放 tooltip。

#### F22 ｜ P3 ｜ 进度没有时间预期

- **用户场景**：255 条翻到 137 条时，用户无法判断还要 1 分钟还是 10 分钟、能不能先去干别的。
- **证据**：帧 3 只有计数与条形进度。
- **摩擦类型**：等待不确定性。
- **修改建议**：采集前若干条的速度后，步骤行补一句「约还需 X 分钟」（可粗粒度，避免承诺过准）；或至少在开始时提示量级（见 F5）。

#### F23 ｜ P3 ｜ 展开区里「普通用户看这里就够」是元话语，且与顶部提示重复

- **用户场景**：用户展开插件，正文里突然出现一句对读者说话的指令，抢了作者简介的注意力；内容又和页顶提示行几乎重复（都在说「点应用汉化，会自动重载」）。
- **证据**：帧 2 展开区 `普通用户看这里就够：点上面的「应用汉化」，插件会自动重载，界面立刻变中文。` 与页顶 hint。
- **摩擦类型**：文案层级混乱。
- **修改建议**：展开区首行改为**状态陈述**而不是指令（如「这个插件有 78 条界面文本，已翻 65 条；应用后会自动重载」），指令统一留在页顶 hint；若保留引导语，用更弱的样式（灰字、单行）。

#### F24 ｜ P3（建议）｜ 列表里的一行简介仍是英文，可复用自家简介汉化表

- **用户场景**：这个页面的用户十有八九读英文吃力，但每行的英文简介（`Show treasure maps and decipher markers on the map.`）是原文直出。FireGaze 自己的「简介汉化」表里很可能已有这条中文。
- **证据**：帧 1 / 2 列表行简介均为英文。
- **摩擦类型**：可避免的阅读成本。
- **修改建议**：如果本机词表里已有该插件简介译文，列表行优先显示中文（悬停看原文）；没有则保持英文。属于增强，不是缺陷。

#### F25 ｜ P3 ｜ 还原图自身的三处保真问题（会被当成验收依据）

- **证据**：① 帧 4 工具栏仍是 `已汉化 12`，但同屏 BOCCHI 刚完成（应 +1），计数不自洽；② 窗口标题画成 `插件汉化 — Orbwalker###FireGazeUITextEditor` 与 `翻译设置###FireGazeUITextSettings`——ImGui 会把 `###` 之后的部分当作 ID 不显示，真实标题栏只会显示前半段，图应画可见形态；③ `ui-mockup-uitext-editor.html` 头部注释声明 3 帧（含「帧 2 设置入口」），实际只有 2 帧且标号从「帧 1」跳到「帧 3」；④ 列表图标是字母占位块，不是真实插件图标——「和平时看到的一样」这一点在图上没有被验证。
- **修改建议**：改后图逐条修正：计数随操作更新、标题不带 `###`、帧号连续（或恢复缺失帧）、至少用 2–3 个真实插件图标（含一个加载失败的回退形态）。

#### F26 ｜ P3（需实机确认）｜ 小字号与特殊字形

- **用户场景**：徽标、步骤行、tooltip 都是 12–13px 级别的小字；✔ / ⚠ / ▾ / · 这些字形需要字体覆盖与回退。
- **证据**：HTML 中 `.badge`、`.steps`、`.note` 为 12px，`.psum`、`.pmeta` 为 12–13px；ImGui/Dalamud 的字体由运行环境决定，且用户可调整 UI 缩放。
- **修改建议**：实机在 100% 与 125% 缩放、1080p 与 1440p 下各看一遍：徽标是否压行、`✔`/`⚠` 是否出现豆腐块、长插件名 + 双按钮是否挤压。若字形不可靠，改用文字状态（已翻 / 待确认）代替符号。

## ④ 改完以后建议怎么复验

1. **图与实现同序同数**：出「改后图」，帧内控件、计数、按钮名与实现逐项对照（沿用 FireGaze 既有口径：还原图必须与实现同序同数、样例数据自洽）；本报告 ② 的每条建议在图上都能指到具体改动。
2. **首次用户走查（清空配置、无 key）**：准备三个插件（候选 >100、无文本、已汉化）→ 计时从打开窗口到成功汉化第一个插件；
   - 观察首错点：是否先点错「简介汉化」；是否找得到「翻译设置」；
   - 一键汉化中途取消 → 再重来：确认保留条数与续跑；
   - 失败注入（断网 / 断代理 / 手动限流）：确认文案、重试、「已翻的不丢」；
   - 完成后核对：行徽标、工具栏计数、「已重载」表述三者一致。
3. **老用户路径**：已汉化插件 → 还原原文（观察确认 / 提示）→ 重新应用（确认译文保留）；编辑一条译文 → 还原 → 再应用（确认编辑不丢）；插件更新 → 自动重打（含让重打失败的注入用例，确认状态可见）。
4. **需实机确认清单**（本报告所有标「需实机确认」项）：悬停 tooltip 存在性与内容；键盘导航（表格编辑、Esc / Enter 行为）；198 行的滚动与表头/工具栏是否常驻；取消按钮在三阶段的实际形态；确认弹窗默认焦点在「取消」；真实插件图标加载与失败回退；FireGaze 窗口关闭后任务是否继续；重载期间窗口稳定性；12–13px 文字与 ✔/⚠ 字形在 100% / 125% 缩放下的表现。
5. **术语与文案一致性自检**（防图与实现漂移）：导出实现里全部用户可见字符串，按 `汉化 / 翻译 / 候选 / 灰名单 / 不翻 / 补丁 / 重载 / 429 / 第三方` 逐条过表，确认与恢复图逐字一致、无两套叫法并存。
6. **建议的下一轮 skill**：先交 `usability-heuristic-reviewer` 对「确认 / 撤销 / 错误预防 / 一致性与标准」做一轮对照评审；改图后交 `wireframe-critic` 复核编辑器两帧（表格交互与筛选模型）；失败与耗时文案交 `error-and-time-metrics-analyzer` 定稿。
