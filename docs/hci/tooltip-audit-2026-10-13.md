# 按钮悬浮文字（Tooltip）第一性原理审计

- 日期：2026-10-13
- 方法：`awesome-skills/first-principles-skill`（First Principles Thinking v0.2.0）五阶段流程
- 范围：`src/FireGaze` 全部 `SetTooltip` 调用点，共 **101 处**（按钮、复选框、列头、灰字、数据回显）
- 结论摘要：**0 条纯开发者信息；8 条（8%）夹带开发者机制细节——2026-10-13 已按第 4 节全部改写；其余约 93 条（92%）以用户需要的信息为主**

---

## 1. Problem Essence

**核心问题（一句话）：** 悬浮文字应在用户「手已经放上去」的那一刻，用一句话回答「按下它会发生什么」；任何不改变这次点击决策的句子都是噪音。

**成功标准：**
1. 每条 tooltip 都能对应到用户的三种动机之一：① 这按钮干什么；② 为什么是灰的 / 为什么是它；③ 点了会怎样（成功、失败、能不能恢复、隐私与范围）。
2. 没有句子是为了「开发者想记录实现」而存在（目录名、并发数、超时、反射/内部字段、缓存实现等）。
3. 风险与可逆性信息不能删（「不可恢复」「会被覆盖」「不带账号信息」属于用户决策必需）。

## 2. Assumptions Challenged

| 假设 | 质疑 | 判定 |
|---|---|---|
| 悬浮文字越多越友好 | 悬浮是「二次确认」通道，只有一次机会、不可搜索、不能回看 | 弃用 |
| 写清机制细节能建立信任 | 用户要的是「后果 + 能否恢复」，机制不改变决策；机制只该进日志和排障 | 修正为「只留后果与可逆性」 |
| 默认值 / 持久化行为需要写出来 | 用户可以观察到行为本身；状态行与检查框已表达 | 只保留影响决策的（如「会被保存」→ 删） |
| 文案随实现演进自然生长 | 文案是产品的一部分，应独立于实现审查 | 保留为规则 |
| 灰字解释是必要的补丁 | 灰字（页面级说明）是噪音重灾区，本轮已专项清理 6 处 | 已处理 |

## 3. Ground Truths（不可再分解的事实）

1. 用户悬浮的动机只有三类（见成功标准 ①）——不在这三类里的文字不会改变任何操作。
2. 悬浮文字不占有常驻版面，但**占用注意力与阅读信任**：一句看不懂的机制说明会让整屏文案被跳过。
3. 开发者细节（`/icons` 目录、8 并发、120 秒、内部字段、`Info 及以上`、仓库契约）对用户的唯一价值是排障——而那属于日志。
4. 涉及钱的、删数据的、上传数据的、隐私的说明**必须**留在用户面前（可逆性 = 用户决策前提）。

## 4. Reasoning Chain

```
Ground Truth 1（三种动机）
        ↓ 对 101 处逐条问：「删掉这句，用户的点击会不会变？」
        ↓
93 条：删了会变（动作/后果/不可用原因/风险/数据回显）→ 保留
 8 条：删了不会变（用户按标签也能点）→ 机制细节，建议改写
 0 条：整条都是开发者信息 → 无需整条删除
```

## 5. Conclusion

**已落地（2026-10-13）：** 上表 8 条已按建议改写；其余 93 条保持现状。机制细节统一交给日志 / 文档，不进悬浮文字。改写后扫残留，又发现两处警告文案里的机制推测（发现页与体检页的「可能是卫月升级改了内部字段」），也已去掉。

**关键洞察：** 本次审计最反直觉的结论是——**悬浮文字的开发者噪音很少（8%），真正的问题在页面级灰字**（说明行、状态行、来源文件路径、自动更新倒计时）。本轮已按用户要求清理 9 处灰字；后续新增 UI 文案时，按 Ground Truth 1 的三种动机自检即可。

**承认的取舍：** 个别机制说明（如「该设置会被保存」）有微弱的安心价值；删掉后如果用户反馈困惑，再以「后果式」句子补回，而不是恢复机制描述。
