# 参与翻译窗口（FireGaze · ImGui 深色界面）认知摩擦评审

**材料**：`Resources/ui-mockup-contribute-history.png`（4 帧还原图，2×）、`Resources/ui-mockup-contribute-history.html`（结构/尺寸来源）
**使用者假设**：普通玩家，非开发者。目标：① 补缺译文 ② 把改好的译文攒批一键提交 ③ 回看/整理已提交记录
**方法**：`cognitive-friction-detector`（先分清"观察到的事实 / 推断 / 猜测"，只报能落到具体帧与具体用户误判的摩擦点）

---

## 总结

界面骨架是站得住的：上表管"内容"，下栏管"我这批改了什么/我交过什么"，双页签 + 计数 + 批量按钮带基数，方向正确。**没有 P0**。

但这个还原图上有 13 个 P1 级摩擦，集中在三处结构性问题：

1. **两套勾选、两套表格、一套视觉语法**：上表和下栏都长得一样（勾选列 + 无标题的行内按钮列），但作用域完全不同，而"当前选了几条"唯一出现在按钮标签的（N）里。玩家必须先记住自己刚勾的是哪张表，再决定按哪个"清空/删除"。
2. **`（N）` 的含义在同一排按钮里不统一**：`一键提交（3）` 的 3 是"整个待提交列表"，`删除勾选（0）` 的 0 是"你勾了几条"（帧 1 里下栏一行都没勾，但 `一键提交（3）` 仍是 3）。这条足以造成"我只想提交勾的 2 条，结果全发出去了"。
3. **"本地 / 已交出去"这组最关键的状态，只在第 4 帧的删除弹窗里说了一次**。前三帧里玩家无从知道"待提交"和"历史留档"都是本地文件、也不知道留档里那条后来被接受了还是被退回了。

破坏性动作的保护也不对称：`删除所选留档` 有二次确认（帧 4），而 `清空留档`（清掉全部 12 条 / 3 批）和 `清空待提交`（丢掉全部未提交工作）在 4 帧里都没有任何确认。

**结论：OK with notes** —— 可以继续推进，但上面 3 组 P1 建议在进入实现前先定下来（多为文案/常驻指示器级的小改动，不需要重做布局）。

## 做对的地方（Correct）

- **风险时刻给出了后果说明**：帧 4 弹窗写明"把勾选的 1 条从本地历史留档里删掉。已经交出去的译文不受影响，词表也不会变；只是本地不再留这份记录"，并复述受影响条目"09-22 12:30 提交 · Penumbra / 一行简介"（html 385–386 行）。这是全窗唯一一处把"本地 vs 对端"讲清楚的地方，写法本身是对的——问题只是它出现得太晚、只覆盖了一个动作。
- **批量按钮把基数写进标签**：`一键提交（3）`（147 行）、`重新加入待提交（2）`（319 行）、`删除所选留档（2）`（320 行）→ 按之前能预估影响面。
- **库存可见**：页签带计数（`待提交（3）`/`历史提交（12）`，138–139、300–302 行）+ 底部"共 12 条 · 3 批"（322 行）。
- **合并原来"一堆日期页签"为单个 `历史提交` 页签 + `提交时间` 列**（html 5、10、247 行）——这是本次改动最直接的记忆负担削减。
- **状态用文字**（`你译` 绿 / `机器译` 蓝，114–123 行）而不是仅靠颜色，色觉障碍下仍可读。
- **不可用动作显式置灰**（`翻译所选（0）` 等，105–106 行），避免无效点击。
- **上表画出了可见滚动条**（`.scroll`/`.thumb`，57–59 行）→ 上表"还能往下滚"是可发现的。
- **每行都有就地入口**（`改进…` / `改`），不必靠记快捷路径。
- 帧 1 给了下栏一句定性说明"这一栏是你改过、还没提交的译文"（151 行）。

## 发现（Findings）

> 严重度：**P1** = 会在实现前应修（会导致误操作、任务被卡住、或状态不可判断）；**P2** = 记录备查。
> 证据一律给"帧 + html 行号"。

### A. 歧义（按钮/标签到底会做什么）

**F1（P1）同一排按钮里 `（N）` 是两种含义**
- 现象与证据：帧 1 下栏按钮行 `一键提交（3）`（147 行）— 此时下栏**三行一个都没勾**，3 = 页签计数（`待提交（3）`，138 行）= 全量；紧邻的 `删除勾选（0）`（148 行）的 0 = 当前勾选。同一个视觉容器里，括号数字一个代表"全部"、一个代表"你选的"。
- 触发场景：帧 1/2，下栏勾了 3 条里的 2 条 → 按 `一键提交（3）`。
- 会怎么误判：以为"只提交我勾的 2 条"，实际把没勾的那条也交给维护者；反向地，看到 `（3）` 又以为"不用勾，它自己知道我要提交哪条"。
- 建议改法：把两种语义在标签上分开——全量写 `一键提交全部待提交（3）`，勾选驱动写 `提交勾选（2）`；同时把"当前勾选 N 条"做成一个常驻小字/状态条，而不是塞进按钮。

**F2（P1）同一个"编辑译文"动作有三个名字，且批量与逐条的关系不明**
- 现象与证据：上表按钮行 `翻译所选（0）`（105 行）、行内 `改进…`（114 行起）、下栏行内 `改`（140 行起）。三处措辞不同，位置不同，而任务①（补译文）到底从哪个入口开始，界面没说。
- 触发场景：帧 1，玩家想给 Aetherphone 补译文 → 看到顶上有 `翻译所选（0）`（灰的）和行内 `改进…`（亮的）。
- 会怎么误判：以为要先勾选再按 `翻译所选（N）`；或者点 `翻译所选` 期望"打开编辑框"，实际可能是批量机翻/批量套用——两条路径后果不同却同名近似。
- 建议改法：统一为一个动词（如"编辑译文"），并在每行按钮上体现状态（有译文→`改进`、无译文→`填写`）；`翻译所选（N）` 若真是批量动作，改名为 `批量机翻所选（N）` 之类，避免与"我来翻译"混淆。

**F3（P1）待提交页三个按钮在同一个列表上语义重叠，只有一个带计数**
- 现象与证据：`删除勾选（0）`（148）+ `清空待提交`（149）+ `撤回`（150），三者都会作用在"待提交"这一栏；`撤回` 既无计数也无对象。
- 触发场景：帧 1，玩家想丢掉一条改坏的译文 → 在 `删除勾选` / `清空待提交` / `撤回` 之间选。
- 会怎么误判：想删一条却按成 `清空待提交`（清光全部）；或以为 `撤回` 是"撤销刚才那步操作"（有时确实是这个意思），结果它作用在勾选的条目上。
- 建议改法：`撤回` 明确对象与范围（例如 `撤回勾选（N）` 或 `撤销上一步`，二者只能留一个）；`清空待提交` 加确认（见 F17/F19）。

**F4（P1）同一个窗口里有两个"撤回"**
- 现象与证据：顶栏 `撤回添加（0）`（106 行）与下栏 `撤回`（150 行）同屏出现，分属"我的库"和"翻译"两件不同的事。
- 触发场景：帧 1，玩家在翻译流程里看到"撤回添加"。
- 会怎么误判：把 `撤回添加` 当成撤回翻译提交；或点错按钮。
- 建议改法：`撤回添加` 加限定词（`撤回加入我的库（N）`），或者把"添加到我的库/撤回添加"移出本窗口（见 F22）。

**F5（P1）"全选当前/清空勾选"的作用域，和表头那个像复选框的"☐"**
- 现象与证据：`全选当前`（105 行）里的"当前"没有指向；`清空勾选`（105 行）没说清哪张表的勾选；两张表的勾选列表头都是静态文本 `☐`（thead：112、138 行），看起来像"全选"控件但不可点。
- 触发场景：帧 1，玩家在下栏（待提交）按 `全选当前`。
- 会怎么误判：以为"当前"= 当前页签（下栏），结果作用于上表；或点表头的 `☐` 期待全选，什么也没发生。
- 建议改法：把选择动作放到它所属的容器里（每张表自己的工具条：`已选 N 项 · 全选本表 · 清空`），表头 `☐` 换成真正的全选控件或干脆去掉。

**F6（P1）"重新加入待提交"是移动还是复制**
- 现象与证据：帧 3 按钮 `重新加入待提交（2）`（319 行），旁边提示"共 12 条 · 3 批"（322 行）；弹窗（帧 4）只说明删除是"本地删掉、对端不受影响"（385 行），没有任何一处说明回加会不会改动留档。
- 触发场景：帧 3，勾两条留档 → `重新加入待提交（2）` → 之后又 `一键提交`。
- 会怎么误判：以为只是"复制回来重做"，结果留档里同一条出现两条（同一插件/字段、两个时间戳）；或者以为回加会把该条从留档移出，数字会从 12 变 10。
- 建议改法：按钮文案写清（`复制回待提交（N）`），并在留档表里为同一"插件/字段"的重复记录标出来源批次；同时说明"重新提交同一条"在对端会是什么结果。

**F7（P1）留档表里"点插件名"是一个不可见的状态变更**
- 现象与证据：帧 3 注解"进去点插件名也能把这一条加回待提交"（247 行），但表里插件名是纯文本单元格（308 行 `Penumbra`，无下划线、无强调、无按钮），且**同一行同时提供勾选 + 按钮**这条主路径，点名字这条路没有任何视觉提示。
- 触发场景：帧 3，玩家想"看看 Penumbra 这条是什么"，或想按插件筛一下 → 点了 `Penumbra`。
- 会怎么误判：点名字在表格里的通行含义是"跳到/筛到这个对象"，这里却是**改写待提交列表**的动作；玩家会在没察觉的情况下给自己加了待办，且没有撤销提示。
- 建议改法：留档表补一个显式行内按钮（`加入待提交…`/`查看`），或者把插件名做成真链接样式（下划线/强调色 + 悬停提示"加入待提交"）；若点击要保留，就要有即时反馈（见 F17）。

**F8（P1）上表"译文"列没说是哪个字段；缺译文字段的入口看不见**
- 现象与证据：上表列头是 `原文 / 译文`（thead 112 行），但"字段"这一维只在下栏出现（下栏列头 `字段`，138 行）。比对可见：Questionable 上表 `译文`＝"自动完成受支持的任务…"（116 行）＝它的**一行简介**；而它的 `插件名` 译文"任务助手"只出现在待提交表（142 行），上表 `插件名` 列永远显示英文 `Questionable`。即：每个插件有 3 个可译字段，上表只呈现了其中 1 个（一行简介），且没有说明。
- 触发场景：帧 1/3，玩家读到 Questionable 一行，想知道"插件名汉化了没有"。
- 会怎么误判：以为 Questionable 没有中文名（其实自己刚写了"任务助手"还在待提交）；以为上表一行 = 一个翻译单位，漏掉插件名/插件详情两处缺译文。（任务①被卡住的主要来源）
- 建议改法：三选一——① 上表 `译文` 列头写成 `一行简介译文`；② 按"字段"行展开（一个插件 3 行，或行内显示 3 个字段的译文摘要 + 各自状态点）；③ 行内 `改进…` 打开后默认列出三个字段与其状态（缺/机翻/你译/待提交）。无论选哪种，都要有一个"哪些字段还缺"的可见线索。

### B. 隐藏状态（本地留档 vs 已交出去；删掉之后会怎样）

**F9（P1）"这是本地的"这件事，只在删除弹窗里说了一次**
- 现象与证据：唯一披露在帧 4 弹窗"从本地历史留档里删掉……只是本地不再留这份记录"（385 行）。前三帧里 `待提交（3）`、`历史提交（12）`、`共 12 条 · 3 批` 都没有"本地"字样；帧 1 的说明句"这一栏是你改过、还没提交的译文"（151 行）也没说存在哪里。
- 触发场景：帧 1/3，玩家看到 `历史提交（12）`，据此认为这是服务器上的记录。
- 会怎么误判：以为"历史提交"是服务端事实（因此重装插件、换电脑、换角色后它还在）；于是在本地文件丢掉/重置时，对记录消失毫无预期，也不会想到要自己备份。
- 建议改法：在 `历史提交` 页签旁常驻一句（如页签下的固定副标题）"以下是你本机记录的提交历史（存本地，重装/换机器不会带过去）"；把帧 4 弹窗里那句"本地"提前到常态位置，而不是只在危险动作时出现。

**F10（P1）留档表既看不到"结局"，也读不到全文**
- 现象与证据：帧 3/4 留档表列头只有 `☐ / 插件 / 字段 / 译文 / 提交时间`（306 行），**没有状态/结果列**；`译文` 长文本被省略号截断（309 行"一个运行时的模组加载与管理框架，可在不重启游戏的情况下热插拔…"），且留档表**没有行内按钮列**（对比下栏待提交表有 `改`，140–142 行），因此截断后无法展开。悬停只承诺显示"这条是什么时候写的"（247 行），不是全文。
- 触发场景：帧 3，任务③"回看/整理已提交记录"——玩家想看自己上次提交的插件详情译文。
- 会怎么误判：以为留档里存的就只有这半句；或以为"历史提交"里能看到"有没有被采纳"（看不到），从而反复重新提交同一条。
- 建议改法：给留档表加一列结果（`待审 / 已采纳 / 被替换 / 被驳回`）与一个行内 `查看…`（只读弹窗，显示全文 + 提交批次 + 原值）；若不打算做结果列，就必须在界面上明确"这里只是本地发出记录，不含审核结果"，并指出到哪里看结果（见 F11）。

**F11（P1）"我提交过的东西后来怎么了"没有归属屏**
- 现象与证据：上表筛选里同时有 `机器译`、`我提交过`、`待复核`（95–103 行），而 `状态` 列只演示了 `你译`（114 行）与 `机器译`（115 行起）两个值；`待复核` 从不作为状态值出现，`我提交过` 与 `你译` 措辞不同、指向不明。
- 触发场景：帧 1，提交完（假设切回上表）想确认"我交的那 3 条现在是什么状态"。
- 会怎么误判：在 `历史提交` 里找审核状态（找不到，F10）；在同一行上看到 `你译` 就当成"已生效"；把 `待复核` 理解成"需要我复核别人"而不是"我的东西在等别人复核"。
- 建议改法：统一一套状态词表并说明方向（`缺译文 / 机器译 / 我译（未提交）/ 已提交·待审 / 已采纳 / 被退回`），并在上表状态列里支持 hover/详情能看到这套完整状态；`待复核` 改成 `已提交·待审`。

**F12（P2）"连着已停用的库"默认勾选，后果未说明**
- 现象与证据：该复选框在 4 帧里都是勾选态（102 行等），旁边 `显示图标` 是未勾选（101 行），两个混在同一行、无分组标题。
- 触发场景：帧 1/3，玩家在列表里看到来源库已停用的插件。
- 会怎么误判：以为"能列出来 = 可以/值得提交"；花时间给已停用仓库补译文，而这些译文可能永远不会到玩家手里。
- 建议改法：默认不勾选，或在已停用来源的行上加标记（灰化 + `库已停用`）；并说明对该库的提交会被怎么处理。

### C. 记忆负担

**F13（P1）两张表各自独立勾选，唯一的选择指示器藏在按钮标签里**
- 现象与证据：上表勾选列（112 行）+ `全选当前/清空勾选`（105 行）；下栏勾选列（138 行）+ `删除勾选（N）`（148 行）；没有任何常驻的"已选 N 项"指示，`（N）` 只在按钮上（且 F1 说明它含义还会变）。
- 触发场景：帧 1/3，玩家先在**上表**勾了 3 行去 `翻译所选`，再切到下栏勾 1 行 → 按 `清空勾选`。
- 会怎么误判：以为 `清空勾选` 是清下栏（因为视线在下栏），实际清的是上表；或者反向——在下栏点了 `删除勾选（1）` 却发现别的行还亮着高亮（上表残留选中态），以为程序坏了。
- 建议改法：每张表配自己的选择状态条（"已选 N 项 · 清空"），或让"离开某张表时自动清空该表勾选"成为明确规则并写出来；`全选当前/清空勾选` 移入各自表格容器。

**F14（P1）同一批对象有 5+ 个名字**
- 现象与证据（同一个对象多个词）：
  - 未提交工作：`待提交`（138 行页签）/ `这一栏`（151 行）/ `你改过、还没提交的译文`（151 行）/ `勾选`（148 行）；
  - 本地历史：`历史提交`（139 行页签）/ `历史留档`（247、319 行）/ `留档`（320、321 行）/ `记录`（385 行）/ `共 12 条 · 3 批`（322 行）；
  - 新增未解释概念：`词表`（385 行，全窗仅此一次）。
- 触发场景：帧 3→4，玩家读完页签、按钮、弹窗，需要判断"清空留档"删的是不是"历史提交"里的东西。
- 会怎么误判：以为 `留档` 和 `历史提交` 是两样东西（例如"留档=本地副本、历史提交=服务器"），从而在删除时犹豫或点错；把 `词表` 理解成自己没见过的功能。
- 建议改法：各留一个词——未提交统一 `待提交`，本地历史统一 `提交历史（本地）`；页签、按钮、弹窗全部对齐；`词表` 要么给出解释，要么删掉（弹窗里那句可以改成"你交出去的译文不会因此改变"）。

**F15（P2）"批"是数据模型里有、界面里没有的东西**
- 现象与证据：提示"共 12 条 · 3 批"（322 行）说明存在"批"这个单位，但表里只有重复的 `提交时间`（308–313 行），没有批次分组、没有批次分隔、无法按批操作。
- 触发场景：帧 3，玩家想"把 09-21 那批全删掉"。
- 会怎么误判：逐条比对时间戳来认批；或者误以为 12 = 12 批。
- 建议改法：按批次分组（组头 `09-21 20:58 · 3 条`，组内可一键勾选整批），或把 `提交时间` 列改成"批次 N · 09-21 20:58"，让"批"可点可选。

**F16（P2）顶栏 12 个筛选控件没有分组标题，且默认不是玩家最需要的那个**
- 现象与证据：搜索（90 行）+ 搜索范围 3 勾（91–93）+ 5 个单选（96–100）+ 2 个复选框（101–102，与单选同行、无标题）+ 视图 2 单选（104 行）。任务① 最需要的是 `缺译文`，但默认是 `全部`（96 行），且它与 `机器译` 是两个不同的待办集合。
- 触发场景：帧 1 首次打开。
- 会怎么误判：以为默认列表就是"需要我干的活"；把 `显示图标` 当成筛选器（实际是显示开关）；不知道 `缺译文` 与 `机器译` 是两个待办池。
- 建议改法：给两组控件加标题（`筛选：[全部][缺译文][机器译]…`、`显示：[ ] 图标 [ ] 已停用库`），把显示类控件移到视图/设置处；对任务① 提供更直接的入口（例如默认勾选 `缺译文`，或顶部给一句"还有 N 个插件缺译文 · 去补"）。

### D. 反馈缺失

**F17（P1）"一键提交"没有任何进行中/成功/失败/去哪了 的反馈位**
- 现象与证据：帧 1 的 `一键提交（3）`（147 行）是 primary 主按钮；全窗找不到任何状态行/日志行/toast 位置，"提交后会怎样"在界面文字里完全没有（只在 mockup 的 title 里写了"交给维护者"，5 行）。整窗的可变反馈只有页签计数与 `（N）`。
- 触发场景：帧 1，玩家按 `一键提交（3）`——网络请求必然有耗时与失败可能。
- 会怎么误判：按钮按下后界面如果只把 `待提交（3）` 变成 `待提交（0）`、`历史提交（12）` 变成 `（15）`，玩家可能根本没注意到；看不到"正在提交/提交成功/失败原因"，于是反复按，或在失败时以为已经发出去了。
- 建议改法：在按钮行右侧或下栏底部留一个常驻状态区（`上次提交：09-22 12:30 · 成功`；进行中 `正在提交 2/3…`；失败 `提交失败：网络超时 · 重试`）；失败时保留待提交内容并提供重试。同时给出提交目的地的一句话（哪里/给谁/是否需要登录）。

**F18（P1）批量提交前没有复核面；也找不到"上次提交时间"**
- 现象与证据：待提交表列头 `☐ / 插件 / 字段 / 译文 / (空)`（138 行），只有**新值**，没有原值、没有"改了什么"的标记；帧 1 顺手暴露了一个更麻烦的例子——待提交里 Penumbra/一行简介的值（140 行"运行时模组加载与管理器。"）与上表 `你译` 的值（114 行）**完全相同**，界面上无法判断它到底是"已生效"还是"还等着发"。另外：即使 `历史提交` 里就有时间戳（308 行），窗口内没有任何"上次提交：…"的常驻显示。
- 触发场景：帧 1，勾了 3 条准备 `一键提交`（这是提交给维护者之前最后一道闸）。
- 会怎么误判：不看就发（因为没有可看的东西），把机翻味或改坏的条目一起交出去；把"值相同"的 pending 条目当成"新的改动"再提交一次；提交完不知道刚刚发出去了几条、什么时候发的。
- 建议改法：待提交表加"原值/生效值"对照（或行内 `对比…`，只读并排显示旧值→新值）；给每条 pending 一个来源标记（`新译 / 改了机翻 / 与线上相同`）；`一键提交` 前给一步确认预览（"将提交 3 条：Penumbra 一行简介、Penumbra 插件详情、Questionable 插件名"）；把"上次提交"时间放到 `一键提交` 旁边。

**F19（P2）动作"之后"的状态没定义，也没有撤销**
- 现象与证据：帧 4 之后的表/计数/空态都没有画；4 帧里没有任何 undo 提示；`清空留档`（321 行）与 `清空待提交`（149 行）在两个页签上都是普通按钮，而 `删除所选留档` 有确认（320→帧 4），保护强度不对称。
- 触发场景：帧 3，误按 `清空留档`；或帧 1 误按 `清空待提交`。
- 会怎么误判：以为"清空"有确认（因为旁边删除有）；在本地未提交工作被一键丢光后，找不到任何恢复路径（帧 4 弹窗明确说本地删掉就没了）。
- 建议改法：① 给 `清空留档` / `清空待提交` 加与 `删除所选留档` 同级的确认（数量写进标题，如"清空全部 12 条本地留档？"）；② 至少给 `清空待提交` 提供一次撤销（在状态区显示"已清空 3 条 · 撤销"）；③ 删除留档后定义行数/计数变化与空态文案。

### E. 注意力切换（上下两块表格会不会打架）

**F20（P1）两张表共用同一视觉语法，但作用域不同；同一内容在两处重复出现**
- 现象与证据：上表和下栏表都有 `☐` 标题列（112 / 138 行）和**无标题的行内按钮列**（`<th style="width:56px"></th>` / `<th ... width:52px></th>`，112 / 138 行）；同一个对象 `Penumbra / 一行简介` 在两张表各出现一次且文本相同（114 与 140 行）。
- 触发场景：帧 1，玩家看到 Penumbra 在两处都有 → 决定在哪操作；或先在上表勾选，再用下栏的 `删除勾选`。
- 会怎么误判：把两张表看成"同一份数据的两种显示"（其实是"内容源"与"我的待办/留档"）；在错误的表里勾选；不知道 `改` 和 `改进…` 会不会同步到另一处（明显不会，但没有提示）。
- 建议改法：① 给两张表各加一行小标题（上：`插件清单（内容）`；下：`我的提交工作区`），并把无标题的行内按钮列改名（`操作`）；② 下栏行内加一个醒目的来源标记（`= 上表这一行`）或反向在上表对应行加一个小点表示"此项有本地待提交"；③ 明确写一句"两张表的勾选互不影响"。

**F21（P1）缩放窗口只让上表变高，下栏固定；下栏还没有画出滚动条**
- 现象与证据：`.ws { flex: none }` + `.wsbody { height: 158px; overflow: hidden }`（61、65 行），`.topwrap { flex: 1 1 auto; min-height: 0 }`（55 行）；上表有单独绘制的滚动条（57–59 行），下栏 `.wsbody` 没有任何滚动条/行数指示，4 帧里 `历史提交（12）` 只画了 6 行（帧 3，308–313 行）、帧 4 只画 2 行。帧 2 的注解也说"拖动窗口边缘就能看到更多"，但那指的是上表。
- 触发场景：帧 3，玩家想把 12 条留档一次看全 → 拉高窗口（帧 2 教的方法）。
- 会怎么误判：认为"历史提交只有 6 条"；或者拉高窗口后发现没变化，以为界面坏了；反过来，列表变长（例如 50 条）时下栏会怎样完全不可知。
- 建议改法：① 下栏给一个和上表同款的可见滚动条或行数提示（`显示 6 / 12 条`）；② 让下栏也能随窗口增长（例如 `.ws` 给一个合理的 max-height 或可拖拽分隔条），至少在最小尺寸下不至于把上表挤没；③ 在提示里把"共 12 条"改成"共 12 条（向下滚动查看）"。

**F22（P2）本窗口任务之外的控件占着最显眼的操作行，而且撞词**
- 现象与证据：`添加到我的库（0）` / `撤回添加（0）`（106 行）在 4 帧里全是禁用（0）态，却固定出现在上表按钮行；同时与下栏 `撤回`（150 行）撞词（见 F4）。

- 建议改法：移出本窗口（放到"插件安装器"页签），或在无选择时隐藏；若必须保留，改名 `加入我的库（N）` 并与翻译动作之间加视觉分隔。

**F23（P2）帧 4 与前 3 帧的同一窗口并不一致**
- 现象与证据：帧 1–3 在"搜索行（89–94 行）+ 5 单选 + 2 复选（95–103 行）+ 视图（104 行）+ 按钮行（105–107 行）"之后才是表格；帧 4 只有"搜索行（339 行）+ 5 单选（340–346 行）+ 视图（347 行）"就接表格（348 行起）——**缺了 `显示图标 / 连着已停用的库` 和 `翻译所选（0）…` 那一行**。另有帧 3 第 317 行多出一个 `</div>` 把 `wsbtns` 挤到 `.ws` 之外（318–323 行），渲染上表现为提示"共 12 条 · 3 批；进去点插件名…"被折到第二行。
- 触发场景：任何读者对照 4 帧推断"弹窗期间哪些控件可用"。
- 会怎么误判：评审者/实现者以为弹窗打开时全选/翻译所选类控件会消失或不可用；也可能按帧 4 直接裁掉那两行控件。

**F24（P2）关键信息走悬停，手柄玩家可能拿不到**
- 现象与证据：帧 3 注解把"这条是什么时候写的"放在悬停里（247 行），`重新加入待提交` 的替代路径也是"点插件名"（247 行）；FF14 是支持手柄的游戏，而 hover-click 类交互在手柄导航下通常不可达。

- 会怎么误判：看不到逐条写入时间，也无法触发行内 `改`/`改进…`（若这些没有焦点态）。
- 建议改法：把"写入时间"从悬停改成列或次级文本；确认所有行内按钮在键盘/手柄导航下可获得焦点并有焦点高亮。（这一条需要确认插件本身是否支持手柄导航——见开放问题）

- 建议改法：补两帧：① 620×460 的默认态；② 待提交 30 条 / 留档 50 条时的下栏（含滚动条与计数）。

**F26（P2）禁用态的文字对比度偏低，而禁用的按钮恰好带着选择计数**
- 现象与证据：`.btn.disabled { opacity: .45 }`（CSS），禁用按钮文字 ≈ `#e4e4e4` 在 45% 不透明度下叠在 `#3c3c3c`/`#191919` 上，14px 文字的对比度明显低于 4.5:1；而这些按钮上写着 `翻译所选（0）`、`删除勾选（0）`（105、148 行）。
- 触发场景：帧 1/3，玩家想确认"我到底选了没有"。
- 会怎么误判：看不清（0）而误以为按钮只是"暂时不可用"，去找别的地方看选择数（别处没有）。
- 建议改法：禁用态不要用整体透明度压字色（改用独立灰字色，保证 ≥4.5:1）；让选择计数出现在非禁用元素上（F1/F13 的常驻状态条一并解决）。

## 证据 vs 推断

**观察到的事实（可直接核对 html）**
1. `一键提交（3）` 出现在下栏**未勾选任何行**的状态（147 行 vs 140–142 行全部 `chk` 无 `on`）；相邻 `删除勾选（0）` 随勾选变化（148 行）。
2. 上表 `译文` 列对 Questionable 显示的是"一行简介"的译文，而不是它 pending 的 `插件名` 译文"任务助手"（116 vs 142 行）→ 上表每行只呈现一个字段。
3. `历史提交` 表没有结果/状态列，`译文` 列对长文本截断且无行内按钮列（306–313 行）。
4. `.ws` 不参与弹性分配、`.wsbody` 固定 158px 且 `overflow: hidden`（61、65 行）；上表有独立绘制的滚动条（57–59 行），下栏没有。
5. `本地` 只出现在帧 4 弹窗（385 行）。
6. `清空留档`（321 行）、`清空待提交`（149 行）无确认；`删除所选留档` 有确认（320 行 → 帧 4）。
7. 帧 4 的顶栏比帧 1–3 少两行控件（339–347 行 vs 89–107 行）。
8. 两张表的行内按钮列都没有列标题（112、138 行）；勾选列标题是静态文本 `☐`。
9. 帧 3 第 317 行多一个 `</div>`，使 `wsbtns`（318–323 行）落在 `.ws` 之外。

**推断（我在报告里已标出的假设，需要确认）**
- A1：`一键提交（3）` 是"提交全部待提交"，而不是"提交勾选的"。依据是 1（未勾选但仍显示 3，且 3 = 页签计数）。**若实际是"未勾选=提交全部、有勾选=提交勾选"，F1 的严重度不变，只是文案方向要改。**
- A2：上表 `译文` 列固定映射"一行简介"。依据是 2（两处比对一致）。
- A3：任务① 的主要入口是 `改进…`，而 `翻译所选（N）` 是批量动作。依据只有措辞，未在任何帧中演示。
- A4：`重新加入待提交` 不会从留档移除条目（因为"共 12 条"在回加后没有给出新数字）。这只是"未见证据"，属于开放问题。

**不敢下结论的一点（写明，避免误导）**
- 在 2× 缩略的 PNG 上，上表里 `Penumbra`、`Questionable` 两个插件名**看起来**比其它行偏蓝（强调色），而 html 里这两格没有任何颜色类（114、116 行），全篇也没有任何图例解释"插件名变色=什么"。这可能是缩放/抗锯齿造成的观感偏差，也可能是 PNG 与 HTML 不同版本。**不写成 finding**，列为开放问题 Q14：如果确实是有意的状态编码（例如"该插件有本地未提交内容"），那它属于"只靠颜色、无图例"的隐藏状态，必须补文字/图例；如果不是，则该 PNG 与 HTML 不一致，需重出。
