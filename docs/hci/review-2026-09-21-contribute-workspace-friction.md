## Summary
本次评审的问题集中在四类：**状态撒谎**（P0-1）、**同一屏多个同形控件的口径/作用域不清**（P1-2、P1-3、P1-4、P1-5）、**跨界反馈闭环缺失**（P1-6、P1-7）、**布局把两栏割裂**（P1-8），以及评分页专属的**不对称票数误导**（P1-1）。原型本身还有若干自洽性与实现不一致（P2-1、P2-3、P2-7），会直接误导按原型施工的人。目标用户是"愿意顺手做汉化的卫月用户"，核心任务是"找到缺译 → 改一条 → 攒起来提交 → 回头看交了什么"，本报告的每条发现都挂在这条任务链上。

## Findings
### P0-1 「一键提交」的"已提交"是假的
- 位置：`ContributeWindow.cs:1948-1962`（`SubmitContributions`：`OpenIssue(compact:false)` **之后无条件** `this.store.ArchiveSubmission()` + `SetStatus("已提交 {count} 条…")`）；`OpenIssue` 的失败分支 `:2018` 只写 `SetStatus("打开浏览器失败：…", isError:true)`，紧接着被成功文案覆盖；`ContributionsStore.cs:234`（`ArchiveSubmission` 里 `undoStack.Clear()`）。原型侧：帧 1「一键提交（3）」（html:143）及悬停说明"打开 GitHub 的提交页…按 Submit 发出去；发完这里会清空"。
- 触发条件：点「一键提交（3）」后浏览器被系统拦下 / 玩家关掉了标签页 / 没按 Submit；或玩家按了 Submit 但 Action 判"一条都不收"（`validate-contribution.yml` 会自动 comment + close）。
- 后果：屏幕状态与外部世界相反。待提交被清空、凭空多出一个只读页签"2026-09-21（6）"、状态栏写"已提交 3 条"，而 GitHub 上什么都没有；`undoStack.Clear()` 把「撤回」也一起废掉，编辑入口只剩只读留档，玩家只能凭记忆重打。这是"提交成功"这句谎话，且正好发生在最需要可信度的动作上。
- 改法：`OpenIssue` 返回 bool（`Process.Start` 成功且 URL 非空才 true），只有 true 才 `ArchiveSubmission`；失败时保留待提交、保留错误状态栏（后续不得覆盖）。更稳的做法：把"清空+留档"推迟到玩家机器回来说一句"我提交好了"（或在 Action 回评有可用条目之后）。
### P1-1 评分页：👍 有票数、👎 没有，底部提示还替这个不对称背书
- 位置：帧 3 `👍 赞成 7` / `👎 反对`（html:250-251）、`👍 赞成 3` / `👎 反对`（:260-261）、`👍 赞成 12` / `👎 反对`（:295）、`👍 赞成 4`（:301）；帧 3 底部提示「悬停 👍 / 👎：只统计票数，不显示谁投的；再点一下取消」（:322）。
- 触发条件：读任意候选行（这就是该视图的主任务）。
- 后果：① 不对称数字会被当锚点 —— "7 赞成 + 反对（无数字）"最自然的读法是 7:0，玩家据此认定"稳选"，而反对票可能更多；② "只统计票数"这句话听起来两边都统计、只是不署名，会强化误解；③ 点 👎 后唯一的反馈是底色变红，没有任何数字会动，玩家无法确认反对被记下，"再点一下取消"更是无从验证（无数字可回退）。
- 改法：① 底部提示改为"👍 显示总票数；👎 只标记你自己投没投（票数不公开）"；② 👎 在"已投"时用文字写状态（`👎 已反对`），不要只靠红底（html:61 的 `.vote.off.on` 目前是唯一信号）；③ 若"反对票数不公开"是刻意设计，在组头或首行给一句解释，否则它必然被读成 0。
### P1-2 「每页 10 条」的单位不清，三处计数互相打架
- 位置：帧 3 提示「· 每页 10 条 · 只显示有候选的插件 · 共 47 条候选」（html:229）+ 分页控件「第 1 / 5 页」（html:235）；组头计数「候选 2 个」/「候选 1 个」/「候选 3 个 · 赞 ≥ 1 的 2 个」（html:245、:277、:289）；而帧 3 画面只有 4 个插件、6 条候选。
- 触发条件：翻页、以及估算"还剩多少要评"时。
- 后果：① "10 条"到底是候选条数还是插件数无法判定；若是候选条数，一个插件有 3 条候选时第 10 条边界会把同组候选切到下一页，组头与候选分离，玩家失去横向比较的参照；② "共 47 条候选"紧贴"只列赞 ≥ 1 的候选"，玩家会以为 47 已是过滤后的数，而组头又出现"候选 3 个 · 赞 ≥ 1 的 2 个"，两套口径同屏；③ "每页 10 条 / 47 条 / 第 1 页只有 6 条"对不上，玩家会怀疑列表不全（这与 P2-3 是同一类不信任来源）。
- 改法：固定一个单位并贯穿全页 —— 顶部写"共 47 个插件待评 · 本页 6 条候选（每页最多 10 条，同一插件的候选不会被分页拆开）"；组头统一成"候选 N 个（赞 ≥ 1 的 M 个）"；分页旁补"已评 x/47"的进度（现在只有"只看我没评过的"复选框，没有进度）。
### P1-3 下栏按钮组的作用域不看当前页签
- 位置：`ContributeWindow.cs:1586-1725`（`DrawWorkspaceButtons`）—— 一键提交只看 `pending`（:1591），删除只看 `selectedCount`（:1616），撤回只看 `CanUndo`（:1652），**没有任何一处判断 `workspaceTab`**；`selectedRecords` 只在删除/提交时清空（:1902、:1959），切页签不清。原型侧：帧 2 只画出"5 个按钮全部变灰"的结果（html:199-204），没有画出"待提交仍有内容时这些按钮是亮的"这一态。
- 触发条件：帧 1 在「待提交（3）」里勾 1 条 → 切到「2026-09-21（6）」（即帧 2 的画面）→ 「删除（1）」仍然亮 → 点击。
- 后果：玩家盯着留档数据，被删掉的却是当前屏幕上看不见的待提交条目，而且会真实改动词表（`Table.SetTranslation(Previous)`）。状态栏虽写"已删除 1 条待提交译文"，但在留档语境里极易读成"删掉了这份留档"。同理在留档页签上按「一键提交（N）」会把看不见的待提交内容发出去，并把 `workspaceTab` 跳到新批次（画面整体跳变）。
- 改法（最小）：编辑类按钮的启用条件加 `workspaceTab < 0`；或切到留档页签时**隐藏**（而非灰掉）这 4 个按钮。配套：按钮行左端加作用域前缀（"待提交 ·"）。
### P1-4 「删除 vs 清空」的危险样式与破坏面相反，且与上栏「清空勾选」撞名
- 位置：帧 1 按钮行 `一键提交（3）` → `删除（1）`（红色 `.btn danger`）→ `清空`（普通灰）→ `撤回` → `查看历史提交记录`（html:143-147）；同一页上栏另有「清空勾选」（html:108）。实现：删除**没有任何确认**（`ContributeWindow.cs:1616-1631`），清空有二次确认弹窗（:1634-1636 触发、:1692 的 `清空待提交###ConfirmClear`）。
- 触发条件：想清掉勾选，在下栏看到「清空」直接点；或想删 1 条，顺手点了右边看起来更温和的「清空」。
- 后果：破坏面最大的按钮（清掉全部待提交 + 改词表）长得最安全；只删勾选一条的按钮反倒被涂成红色危险色 —— 危险感与真实风险相反。"清空"和上栏"清空勾选"几乎同形，玩家会以为它只是清勾选（上栏那个只动选中集合、不碰词表）。再加上"删除不需确认、清空要确认"，玩家无法建立"破坏性操作会被拦一下"的稳定预期。
- 改法：危险色按破坏面排：「清空全部（3）」用 danger，「删除勾选（1）」用普通色；上栏「清空勾选」改名"取消全部勾选"；删除也加一次确认（或在按钮上写"可撤回"）。
### P1-5 「撤回」的语义边界不可见，而且提交后立刻失效
- 位置：帧 1 / 帧 2 的「撤回」（html:146 / :202，帧 2 灰）；tooltip 只在悬停时说明"把上一次删除 / 清空恢复回来"（`ContributeWindow.cs:1652`）；`ArchiveSubmission()` 里 `this.undoStack.Clear()`（`ContributionsStore.cs:234`）；编辑保存 `SaveEdit`（:1430）不入 undo 栈。
- 触发条件：玩家刚点完「一键提交」，或刚改完一条想反悔，视线落到旁边的「撤回」；或在只读留档页签上看到「撤回」还亮着。
- 后果：按钮只有一个词"撤回"，最自然的理解是通用撤销（"撤回我刚才的提交"）。实际它只覆盖删除/清空，且**提交会把撤回栈清空** —— 最想反悔的时刻恰好不可用。在只读的留档页签上它亮着，更像"能撤回这份留档"，与实际行为（改的是待提交和词表）相反。
- 改法：按钮文字直接写对象并按栈顶动作动态换标签（"撤回刚才的删除（1）"/"撤销清空（3）"）；禁用态 tooltip 补"只有删除 / 清空之后才能撤回，提交不能撤回"；留档页签下不要让它看起来可用（与 P1-3 同修）。
### P1-6 唯一的把关在下游：编辑时无提示，被拒时内容已离开工作区
- 位置：编辑弹窗 `DrawField` 的两个 `InputTextMultiline` 上限 4096、无字数计数、无规则提示（`ContributeWindow.cs:1377-1428`）；规则在 `validate_contribution.py` 的 `FIELD_LIMITS = {Name:40, Punchline:99, Description:999}` 与 `URLISH/HTMLLISH/DENY_WORDS`；提交即清空待提交（`ContributeWindow.cs:1948-1962`）。
- 触发条件：在「插件详情」里写超过 1000 字（帧 1 下栏那条"一个运行时的模组加载与管理框架…"就是长文本），或译文里带了 `https://`、`<b>`。
- 后果：玩家在输入端完全看不到规则，只有 GitHub Action 回评才知道被拒；而那一刻这条内容已经不在「待提交」，只躺在只读留档里（没有"取回"动作），要重做。更麻烦的是 Action 报告按 `InternalName` 列条目（`validate_contribution.py` 报告表格），而界面主要显示 DisplayName —— `InternalName` 只在悬停表格行的 tooltip 里出现（`ContributeWindow.cs:960`），对回"是哪一条"非常费劲。
- 改法：① 三个字段旁显示"已用/上限"并在超限时标红（数字与脚本共用一份常量，避免 40/99/999 两处漂移）；② 提交前在本地跑同一套规则（控制字符/URL/HTML/短词表），把不合规条目在待提交里标红并阻止提交；③ Action 报告同时回显 DisplayName 或译文摘要。
### P1-7 「查看历史提交记录」名不符实，而真正需要看的东西没有入口
- 位置：帧 1 / 帧 2 按钮行末尾「查看历史提交记录」（html:147 / :203）；实现只做 `this.workspaceTab = this.store.History.Count - 1` + 一行状态文案（`ContributeWindow.cs:1666-1685`）；页面文案"可以在 Github（待补完）"（html:83，实机同句并带 `TODO(文案待补)`）。
- 触发条件：玩家想看"我提交的东西过没过校验 / 别人评了什么"。
- 后果：① 按钮名像"打开 GitHub 记录"，点了只是在自己页签里跳一格；若当前已在最近一批留档页签上，点了几乎无可见变化（只有底部一行状态字），像按钮坏了；② 玩家真正需要的提交回执（Action 的评论、issue 被自动关闭）在插件内没有任何入口或提示（`validate-contribution.yml` 的结果只存在于 GitHub 端），而校验失败是常态风险（见 P1-6）。
- 改法：按钮改名「跳到最近一次留档」；另给一个真的能看结果的入口（打开本仓库带标签的 issue 列表），并在提交后用状态栏留下那个 issue 链接。
### P1-8 两栏被固定比例高度和大片空白推开，且两栏之间没有共享锚点
- 位置：`ContributeWindow.cs:202-203`（`bottomHeight = Clamp(available*0.42, 150, 420)`，`topHeight = 剩余 - 62`）；原型把空白写进了结构（`.top{flex:1}`，html:50）：帧 1 上栏只有 5 行（html:117-121），帧 2 上栏只有 2 行（html:173-174），两帧截图里上栏最后一行与下栏页签之间都是大段空白；帧 2 留档表格最后一行（Splatoon 09-21 18:44）到按钮行之间同样是大段空白。
- 触发条件：筛选结果少时（帧 2 是"缺译文"过滤后只剩 2 行的状态）。
- 后果：玩家在处理"改哪一条"时，视线要跨过约占窗口高度 1/3 的空白在上下两栏之间往返；"下栏 = 上栏的工作区"这个隐喻只能靠猜（两栏列名不同：上栏 状态/插件名/来源库/原文/译文，下栏 插件/字段/译文）；两栏各有一个勾选列却互不联动（勾上栏的 Penumbra 完全不影响下栏），而原型给两栏的勾选行都涂了同一种蓝色整行高亮（html:46-47、:117、:136），会让人误以为它们联动。
- 改法：下栏高度按内容自适应（行数×行高 + 页签 + 按钮行，min 150 / max 420），或给分隔条允许拖动；弹窗保存后把下栏对应行滚到可见并短暂高亮（`store.Changed` 已经提供了时机）；两栏之间补一个共享锚点（下栏页签左侧显示当前插件名，或勾选上栏后下栏加"只看勾选插件的改动"）。
### P2（报告项，不阻塞合并）
- **P2-1 有勾选却写（0）**：帧 1 上栏第一行 Penumbra 的复选框是勾上的（html:117 `chk on` + `tr.picked`），同屏按钮却写「翻译所选（0）」（html:108）。实现里标签是插值（`$"翻译所选（{selectedCount}）"`，`ContributeWindow.cs:1129`），所以这是原型写死数字造成自相矛盾；截图里它与加了 `.btn.disabled{opacity:.45}`（html:34）的两个按钮也不好区分，读者判断不出哪个真的可按。后果：读者会照抄错误的启用规则；玩家会怀疑"勾了算不算"。改法：原型让计数与勾选态联动（勾 1 条写 1 且按钮变亮），并把"可按/禁用"两态做出明显视觉差。
- **P2-2 「（N）」口径太多**：同屏出现 翻译所选（0）、添加到我的库（0）、撤回添加（0）（html:108-110）、一键提交（3）、删除（1）（html:143-144）、页签 待提交（3）/2026-09-21（6）（html:128-129）。括号里的数字分别是：勾选的插件数 / 可加库数 / 上次加库数 / 待提交条数 / 下栏勾选条目数 / 每批留档条数 —— 六种口径。改法：括号前把对象写全（"翻译勾选的插件（1）"），派生量（可加库数）改用非数字表达。
- **P2-3 留档页签计数与表格行数对不上**：帧 2 页签「2026-09-21（6）」（html:184）+ 气泡"共 6 条"（html:208），但留档表只画了 4 行（html:191-194），下方还是留白。玩家/评审会以为丢了 2 条。改法：补齐到 6 行，或在表格区明示"共 6 条，当前显示 4 条（可滚动）"。
- **P2-4 同日同条数的两批留档页签会完全重名**：页签文字是 `日期（条数）`（html:129、:185；`ContributionsStore.cs:56`），同一天两次各提交 2 条就会得到两个一模一样的 `2026-09-21（2）`，只能逐个悬停看时间。注：这不是在质疑"日期命名 + 悬停显示具体时间"这条既定前提，只是需要防重名（同日加序号，或把 HH:mm 作为页签副文本）。
- **P2-5 下栏页签可重排**：`ImGuiTabBarFlags.Reorderable`（`ContributeWindow.cs:1529`）。玩家可以拖动只读留档页签，把"从左到右 = 从早到晚"打乱（ImGui 还会记住顺序），之后新增页签可能出现在中间，「查看历史提交记录」跳"最近一批"时与位置直觉不符。改法：去掉 `Reorderable`（ImGui 没有反向的 NoReorder 开关，省略该 flag 即可）。（已核对：这不会造成标签与数据错位，见 Correct 段末。）
- **P2-6 静默上限**：历史留档最多 60 批（`ContributionsStore.cs:99`、:227-229，超出丢最早一批）、撤回最多 10 步（:98、:317-318）、待提交最多 500 条（`Trim`）。原型文案说"本地留档，只读"（html:204），玩家会理解成永久。改法：到上限时给一次可见提示，或在页签行写明"只保留最近 60 批；撤回仅最近 10 步"。
- **P2-7 「清空」的置灰规则原型与实现不一致**：帧 2 把「清空」画成灰（html:201），但实现里 `ImGui.Button("清空###ClearContrib")` 无条件可点（`ContributeWindow.cs:1634`），待提交为空时点它仍会弹出"清空后待提交这一栏就空了…确定吗？"（:1694），确认后状态栏会说"已清空 0 条"。改法：实现里也在 `store.Count == 0` 时禁用，或把原型改成亮态。
- **P2-8 评分页的"投票"与"选择"挤在一行、只靠颜色区分**：帧 3 候选 1 同时出现蓝色左边条（`.cand.fav`）、蓝色 👍 底（`.vote.on`）、蓝色「选它」（`.btn.primary`）（html:295 前后）；候选 2 有红色 👎 底（`.vote.off.on`）却无 fav（html:261）；Penumbra 里 12 票的候选没被选、4 票的被选（html:295、:301）。「选它」按下去会不会顺手给自己投一票、取消「选它」会不会撤掉赞，画面上没有任何线索（规则里也没写，见 Open questions 3）。改法：把投票与选择分成两列（选择用 radio + 文字"已选"，投票只用票数按钮），并把二者的联动关系写清；不要用颜色作为唯一信号。

## Evidence vs assumptions
**证据（可核对）**：上述每条都带 `ui-mockup-contribute-workspace.html` 行号或 `ContributeWindow.cs` / `ContributionsStore.cs` / `validate_contribution.py` / `validate-contribution.yml` 的位置，均为逐行读文件后取得。
**假设（未验证，已标记）**：
1. 帧 3 的 👍 票数被默认为"所有玩家的汇总"。原型没有任何数据来源说明，而现有实现的硬约束是"只存在玩家自己机器的配置目录里，不上传、不联网"（`ContributionsStore.cs` 类注释）。若票数来自服务端，那是一整套新后端，与本次"不调用任何模型、只做规则校验"的提交链路无关。
2. 帧 3 的紫色气泡（html:208）是原型作者画在窗口内的说明框，**不是实机 tooltip**：实机 tooltip 由 `ContributeWindow.cs:1549-1552` 给出，文案是「提交于 {TimeLabel}（本地留档，只读）」，没有"共 6 条"那一行。评审不要把气泡文案当契约，也不要把"气泡压住两行数据"当成实机遮挡问题（实机 tooltip 跟随鼠标）。
3. 帧 2 比帧 1 少了顶部两条说明（"提交的译文优先于机器翻译…"、"本地改动只在你这里生效…"）以及整条上栏操作条（html:98-110）。实现里这些是无条件绘制的（`ContributeWindow.cs:120-124`、`DrawActionBar`）。我按"原型省略"处理、未计入发现；但请注意帧 2 恰好省掉了"点更新词表会整份覆盖本地改动"这条与留档语境最相关的警告。

## Open questions
1. 「只列赞 ≥ 1 的候选」的第 0 票候选谁来投第一票？（这条前提我按规则接受、不当问题提，但答案会决定流程能不能起步）自己提交的译文进候选后，能不能给自己投第一票？「只看我没评过的」是否包含自己提交的？
2. 评分数据从哪来、存在哪？（见"假设 1"）插件当前不联网这一事实，与"赞 ≥ 1 / 共 47 条候选 / 每页 10 条"这类全局数字直接冲突，需要先定数据源再定界面。
3. 「选它」的结果落到哪里：是本地改词表（那就要回答它在「待提交」和留档里怎么出现、会不会绕过「一键提交」），还是变成一次 GitHub 提交（那就要和「一键提交」共用同一条链路与同一个"是否真的提交了"的判定，见 P0-1）？
4. 提交后玩家在哪看到校验结果？目前唯一反馈是 `validate-contribution.yml` 贴回 issue 的评论，插件内没有任何入口，且"一条都不收"时 issue 会被自动关闭。插件需要给出可达链接，否则"提交后没有回音"会成为常态。
5. 留档能不能被"取回"（把某一批留档重新灌回待提交）？删除/清空可撤回，但提交之后没有回退路径；P0-1 修好后这个问题会更突出（玩家会先怀疑"我是不是提交失败了"）。
