# 插件发现 — 信息架构（information architecture）

## 1. 站点/界面层次

```
主窗口 FireGaze
├─ 页签 插件汉化（界面文字汉化；译文包喜欢/下载）
├─ 页签 简介汉化（词表更新；FastDalamudCN 冲突提示）
├─ 页签 仓库体检（库链健康/批量停用删除）
├─ 页签 插件安装器（列表浏览位置 + 已知问题）
└─ 页签 插件发现
   ├─ 搜索（全字段）
   ├─ 排序（六档）+ 换一批（随机档）
   ├─ 筛选（隐藏主库 / 连着已停用的库）+ 计数 + 撤回添加
   ├─ 投稿插件库（可折叠；输入 + 检测 + 顺手加库勾选 + 结果/待收录）
   └─ 插件列表（卡片行）
      └─ 行展开（一行简介 / 详情 / 内部名 / 作者 / 更新 / 推荐 / 点赞 / 库链操作）
```

## 2. 导航模型

- **全局**：主窗口五页签；页签顺序固定（汉化类 → 体检 → 安装器 → 发现）。
- **页内**：无二级页/无路由；全部在一页内（列表 + 行内展开 + 折叠的投稿区）。
- **逃生口**：行内「在浏览器打开」用于离开游戏内环境；无其它出口（不需要）。

## 3. 动作放置

| 动作 | 放置 | 是否紧挨对象 |
|---|---|---|
| 加库 / 启用 | 行右栏 + 展开区 | ✅ 紧挨该插件所在库 |
| 点赞 | 行右栏（+ tooltip 计数） | ✅ 紧挨插件 |
| 展开详情 | 整行（▸ 指示） | ✅ |
| 复制 / 浏览器打开 | 展开区「库链」旁 | ✅ |
| 投稿 | 列表上方独立折叠区 | ✅ 全局动作，不是行级（正确分层） |
| 撤回添加 | 筛选行（全局最近一次操作） | ✅ 全局撤销，不挂在某一行 |

## 4. 深度与广度

- 深度：**1 层**（页签 → 列表；详情在行内、不跳页）。
- 广度：五页签；发现页 1 个搜索 + 1 排序 + 2 筛选 + 1 折叠区。
- 无孤儿页、无超过 2 层的路径。

## 5. 分组逻辑与命名

- 「发现」按**个体（插件）**平铺；库是属性不是分组——与「按仓库视图已删除」一致（用户 2026-10-06 定：只留卡片列表）。
- 命名：页签区分「汉化」（产出译文）与「发现」（浏览收录）；投稿区独立命名避免与加库混。

## 6. 与其它页签的 IA 关系

- 插件汉化页已有「公共译文库（喜欢/下载）」，发现页的「点赞/投稿」是**另一类对象**（插件/库链），两页不得互相搬动作。
- 简介汉化页是「翻译产出」的入口（更新词表），与发现页无导航交叠——词表更新后自动影响发现页数据。

## 7. 结论

发现页的 IA 是**扁平单页**：适合 1900+ 条浏览 + 少量全局动作（投稿/排序/筛选）。若未来加入「按库浏览/收藏夹/关注」，应作为**同一平铺列表的视图切换**，不再新增第二张表（见 `conceptual-model.md` §9 简化建议）。
