## 二、逐条发现
### P1
**ICON-1（P1）「缺图标」把"临时本机状态"和"作者侧持久缺陷"压成一个词，且全页没有一句后果说明 ⇒ 用户无法判断是否值得处理。**
- 证据：设计只给一种后缀（帧 3 `.tip`：`BadApple、BossMod Reborn · 缺图标`）；实现按"名字是否已在 `iconHandles` 里"打后缀（`RepoAuditTab.cs:1170-1172`），**下载中、下载失败、地址已失效、下次开游戏还没下到——全叫"缺图标"**；同一功能里既有的正确表述只在图标条占位格的 tooltip（`:1262`）。
- 为什么重要：①按题目给定的事实，卫月不落盘缓存 ⇒ 每次开游戏图标都处于"缺"的状态，于是**同一个插件这次带后缀、下次不带**，用户会把重现读成"插件出问题了"，而不是"本机又没缓存"；②本页所有其他状态词都带后果句（`内容不合规` 有"后果：…"、`连接失败` 有"建议先重新体检确认" `:657-665`），「缺图标」一句没有，用户只能自己发明含义（插件坏了？没装上？不完整？）；③"是否值得处理"的答案被这个词藏起来了——本机未缓存**不值得处理**（会自动补），地址失效**值得处理但用户处理不了**（要作者改）。最小修法：后缀只标持久事实（`· 图标地址失效`），本机未缓存交回既有的占位格+`:1262` 那句；两类都补一句后果（"只影响列表里的小图，不影响插件运行"）。
**ICON-2（P1）按钮名与真实范围不符：「补齐」是过度承诺，且范围是全机而不是当前视图。**
- 证据：标签 `检查并补齐图标`（HTML 帧 1-3 筛选行末 / `:226`）；实现只遍历 `index.All.Where(x => x.DeclaresIcon && !iconHandles.ContainsKey(...))`（`:1320-1322`）⇒ **作者本来没给 `IconUrl` 的插件既不在计数里、也不会被提一句**（题目事实①），它们永远缺图标；补上是"让卫月下到本会话缓存"（`:1184`/`:1262`），不是持久修复（题目事实：不落盘）。
- 为什么重要：用户点完看到"2 个仍缺"时，无法区分"这 2 个是作者没给（无解）"还是"我网络的问题（可重试）"；连续点两次得到同样结果后，他得到的结论是"功能没用/坏了"，而不是"我该做什么"。最小修法：标签去掉"补齐"（`检查插件图标`），tooltip 与完成句写死范围三层：`只处理作者声明了图标地址的插件（没声明的无法补）；补上的图标只在本次游戏内有效`。
**ICON-3（P1）完成后只报数、不报人、不给下一步 ⇒ 用户知道"有 2 个坏了"，但不知道该做什么。**
- 证据：帧 3 完成句 `…2 个仍缺 ｜ 其中 1 个图标地址已失效 404，1 个下载超时`——没有插件名，没有"再点一次可重试"，也没有"404 要去告诉作者"；实现同样只拼计数（`:1416-1458`）。两条出路性质相反却被并列：**超时=可重试（本地动作）**，**404=不可重试（作者侧缺陷）**；而唯一出路"按钮恢复可点"也没有任何提示（`:1344` 后 `iconAuditRunning=false`）。
- 为什么重要：这是评审重点②的直接答案——他不知道。批量动作的价值本来就是这个出路。最小修法：完成句拆两句可执行的话（超时→再点一次重试；404→图标地址写在作者清单里、需作者修），并把这两类分别写进对应插件格子的 tooltip（沿用本页"解释下沉 tooltip"的惯例）。
**ICON-4（P1）共用易失状态槽造成的"信息不见了"：图标体检会吃掉别人的结果，别人的动作也会吃掉它的结果。**
- 证据：`statusMessage` 是单槽，写入者包括扫描开始/完成/取消（`:825/889/866`）、停用（`:955`）、删除（`:1013`）、撤回（`:639`）。图标体检进行中**每帧无条件重写该槽**（`:1384`），而 `TickIconAudit()` 在状态行绘制之后执行（状态行 `:262-272`，调用点 `:269`）⇒ 图标体检期间并发/紧随的扫描完成消息（"已自动勾选 N 个死链/不合规项"）**只能存活一帧**（约 16ms，实际等于看不见）。反向：`FinishIconAudit` 的 404/超时探测在 `Task.Run` 里回写同一槽（`:1456`，跨线程、无锁、无世代校验），用户在这期间点撤回/删除，其确认消息（`:639`/`:1013`）随后会被这条较旧的结果覆盖。
- 为什么重要：本页把"删除/停用"这种不可逆动作的确认放在这一槽里（"已停用 N 个…可点「撤回」恢复"），被覆盖等于安全感被静默移除；而图标体检自己的结果同样转瞬即逝——正是评审重点⑤说的"信息不见了"。
- 同时暴露基线问题：设计写"复用页面已有的状态行（平时不占位）"，但页面上有**两个**候选——常驻统计行（`共 N 个仓库…`，`:150-158`）与事件状态槽（`:262-272`）；还原图画在筛选行正下方（帧 2/3），实现落在**动作条下方**。验收方照图实现会落在不同位置。
- 最小修法：①在方案里指名是哪一个槽、并写死与扫描/撤回结果同时出现时的优先级；②异步探测回写加世代号（过期不写）；③进行中的进度与完成结果分别落在不同槽位（例如进度用动作条下方、结果并进"上次体检"那一行）。
**ICON-5（P1）进度语义会说谎，而且不能取消：失败越多，进度条越像卡死。**
- 证据：进度条与计数取值是"**已补上**/总数"（`:266` 与 `:1384`：`图标体检Fixed / 图标体检Total`），不是"已处理/总数"。缺图标的常见成因里恰好有"地址失效"——此时计数**一动不动**，直到 45 秒死线（`:1345`）才收尾。还原图帧 1 的文案 `正在下载… 3/12` 更强化"队列进度"的读法。而全页唯一的取消按钮只服务扫描（`:73-90`），图标体检没有取消。
- 为什么重要：45 秒的"0/12 + 进度条不动"会被读成死机；用户要么反复点（按钮此时已灰）、要么关窗口。本页扫描那条动线有取消、有 `d / t` 进度（`:135`），同一页两套反馈语义会互相拉低可信度。
- 最小修法：计数改成"已处理"（`已试 9/12 · 补上 3`），或显示两个数；给同一个取消入口（或进度条右侧"停止"），并把 45 秒上限写进 tooltip。
### P2
**ICON-6（P2）缺少分母，且和旁边那个"12"单位冲突。**
- 证据：帧 2/3 里，上一行是 `共 12 个仓库 … ｜ 本机：已装 9 · 未装 3`，下一行是 `图标体检：12 个插件缺图标`。同一屏两个"12"、两种单位（库 / 插件），而"已装 9"是库数、缺图标数是插件数，用户无法把两组数字对上；也不给"本机共多少个已装插件"作分母。
- 最小修法：完成句写成 `本机已装 X 个插件：Y 个未声明图标地址（作者没给）· Z 个没下载到（本次补上 W）· D 个地址失效（需作者修）`——一句话同时解决分母、单位与"按钮不会修好所有图标"。
**ICON-7（P2）完成句里"作者就没提供"会错误归因到官方库插件。**
- 证据：`noAddress = leftover.Count - leftover.Count(x => x.IsThirdParty && !string.IsNullOrWhiteSpace(x.IconUrl))`（`:1416`），而 `leftover` 只包含 `DeclaresIcon` 的条目——其中**官方库插件是靠 `Dip17Channel` 声明图标**（`InstalledPluginsIndex.cs:26-28`），它们不是"作者没提供"，而是按通道拼地址、本机没下到。文案因此把系统行为说成作者的问题。
- 最小修法：按 `IsThirdParty` 分组后再给文案，官方库那组不要用"作者就没提供"。
**ICON-8（P2）落位在筛选行，暗示"作用于当前视图"；且在没开"显示插件图标"时也会跑并发流量。**
- 证据：按钮与 `只看本机未装的` / `显示插件图标` 同一行（HTML 帧 1-3；`:200-226`），而实际范围是 `index.All`（全机、与筛选/搜索无关），也与 `Config.ShowInstalledIcons` 无关——关掉图标显示时点它，用户看不到任何可见收益（图标条根本不渲染，`:460`）。按题目事实，本机不落盘缓存 ⇒ 每次进游戏都要重下一次。
- 为什么重要：这是评审重点④（"以为要重下所有图标、占流量"）的落点——按钮所在的行表达的语义与它真实的代价相反，而且**点击前没有任何范围/数量提示**（数量只在点下去之后出现）。
- 最小修法：把按钮挪到与图标语义相邻处（`显示插件图标` 右侧紧邻 / 或图标条上的一个动作），tooltip 写明"范围：本机所有已装插件，与当前筛选无关；只下载缺失的图标"。
**ICON-9（P2）还原图与实现分歧 5 处，作为验收基线会被误用。**
①帧 2 的进度条画在筛选行正下方，实现是动作条下方的状态槽（`:259-272`）；
②帧 2 **整块没有动作条**（分隔线、`结果 5 行 · 已选 1`、`撤回/打开备份目录`、工具栏都不见了），帧 1/3 有 ⇒ 新增的那一行占了高度、代价恰好无法验收；
③完成句在 700px 宽下已折成两行（帧 3：`…1 个下` / `载超时`），实现进行中分支用 `TextUnformatted`（`:269`）不折行 ⇒ 最短窗口（560×440，`MainWindow.cs:27-31`，内容区≈528px）下 180px 进度条 + 该句会横向溢出；
④帧 3 的 `.tip` 丢掉了实现里已有的口径句"（这条库一共提供多少个插件，把鼠标放在仓库地址上看）"（`:1145-1148`，即上一轮 AU-2-2 的修法），并把多个名字画成**分行分组、整组只带一次后缀**，而实现是 `string.Join("、")` 单行、**每个名字各带一次后缀**（`:1152-1173`）——名字多时会出现一长串"· 缺图标"把名字淹掉；
⑤帧 2 表格只画 2 行（帧 1/3 画 3 行）。
- 最小修法：帧 2/3 改为与实现同落位、画全动作条、完成句压到一行（或在方案里写死"允许两行"），tooltip 恢复口径句并按实现的分隔形式画。
**ICON-10（P2）文档锚点缺失（沿用本页已立标准，不复述理由）。** `README.md:19` 与 `FireGaze.csproj:14-16` 的功能列表都还没提这项能力。

## 三、归页判断（这个功能该不该在「仓库体检」这一页）
**可以留，但应只留"诊断"那一半，并合并进既有体检动线。** 理由三条：
1. 页面的使命句是"检查链接是否失效、内容是否合规"（`:60`），而"图标地址失效"本质上就是**一个死链**——差别只是它是清单里插件级的 URL；同一页却给它另起了一套进度、另一套状态文案、另一个按钮，而本页唯一的破坏性动作（停用/删除）与它无关，用户的注意力被分到两条不相干的工作流上。
2. 它的"补齐"那一半**已经自动发生**：勾选"显示插件图标"时，每帧都在为所有已装插件轮转取图标（`:271-274` → `PumpIconLookups()` `:1167-1195`）。按钮的独有价值只剩"自费发一次 HTTP 判断 404"。
3. 单位冲突是结构性的：本页所有数字都按"条库链"计，这个功能按"个插件"计，且第 6 条已经说明这两个数字在同一屏互不可对。
**建议落法**：把"图标地址失效"并入 `开始体检` 的检查结果（同一个进度条、同一个取消、同一条完成句、同一套"死链"措辞），删除批量按钮；本机未缓存只在图标条占位格里说（`:1262` 已有）。这样一次性消掉 ICON-2/4/5/8。
