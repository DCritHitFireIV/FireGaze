## Summary
**评审对象**：FireGaze「拦住自动更新」设置页还原图（2 状态帧 mockup）。
**目标用户**（假设）：不读源码的中文 FFXIV 玩家，会用卫月「插件安装器」浏览/安装第三方插件。
**用户任务**（假设）：打开设置页 → 理解这一页在拦什么 → 决定两个开关开还是关 → 之后确认它确实在起作用。
**本次要回答的设计问题**：这一页能否让用户在**不读市场说明、不读源码**的前提下，正确预判「开着会发生什么 / 关掉会发生什么」，尤其是两个默认开启的开关。
**结论**：无 P0（没有崩溃级/契约级缺陷）。**3 项 P1（建议发布前修）**：关掉开关后说明文字原地不动仍在承诺已拦下（F1）；同一功能出现四个名字且正文与说明互相否定（F2）；两个开关的耦合被隐藏，"开着的那一项不生效"（F3）。**6 项 P2（记录/后续处理）**：缺触发时机与关闭后果（F4）、生效无从验证（F5）、三处重复挤掉关键信息（F6）、页签只覆盖一半功能（F7）、还原图与实机布局不符（F8）、跨产物命名与承诺冲突（F9）。
需要说明的方法学边界：**没有任何用户数据**（无测试、无埋点、无工单），所有"玩家会误解"的结论都是基于文案/代码的高风险预测，不是已证结论；F3 是代码路径推理，需实机复核（见 Open questions Q1）。
## Findings
### F1 · P1 · 关掉开关后，说明文字原地不动，仍在描述「已经拦住了」
- **现象**：帧 2 除第一个勾选框外，页面文字与帧 1 逐字相同（`ui-mockup-autorefresh-tab.html:71,74-75,79-80`）。源码里两条说明是无条件绘制的，不随开关值变化（`src/FireGaze/UI/InstallerTab.cs:26`、`:36`）。
- **影响**：用户刚关掉第 1 项，眼睛下方仍是「不再把你正在看的列表顶回顶部」；刚关掉第 2 项，读到的仍是「列表会回到上次的位置」。页面在一项**已被关闭**的情况下继续宣称该行为成立 → 用户会怀疑自己没点中，或以为关了也生效。更糟的是，这个位置本该是页面里**唯一**"关掉会发生什么"的承载点，被浪费掉了。
- **最小改法**（建议）：说明文字随状态切换，或改中性双句式：
  - 第 1 项：「开：后台刷新不会顶掉你的列表／关：后台刷新会把列表和滚动位置重置回顶部」
  - 第 2 项：「开：下次打开回到上次的位置／关：每次都从列表顶部开始」
### F2 · P1 · 同一功能四个名字，且正文与说明互相否定
- **现象**（同一页内）：页签与副标题第三项 = 「拦住自动更新」（`MainWindow.cs:48,69`；HTML:47,49）；开关 = 「…自动**刷新**」（`InstallerTab.cs:21`）；正文 = 「别再自己**刷新**」「自动**重载**」（`InstallerTab.cs:17`）；说明 = 「**刷新**仍在后台进行」（`:26`）。而正文首句「让插件安装器**别再自己刷新**」与说明首句「**刷新仍在后台进行**」在字面上互相否定。
- **影响**：用户拿不到一个可复用的心智模型——同一个事件在页面上被叫成"更新/刷新/重载"三样东西，且"阻止"与"没阻止"同时出现。这直接命中**最危险的误读**：页签/副标题的「**拦住自动更新**」在 FFXIV 语境里最自然的解读是"阻止插件自动更新"（甚至"阻止联网"），而开关默认是**开**的——用户可能因此防御性地关掉它，或带着"我是不是把插件更新堵死了"的疑虑离开这一页。说明里那句「刷新仍在后台进行」本来是安抚，但它用的是"刷新"（用户怕的词是"更新""联网""下载"），安抚与恐惧不在同一词汇里，安抚很难生效。
- **最小改法（标注为**建议**——其中开关整行措辞为产品方指定，不作为错误）**：
  1. 开关整行候选（结果句式，最贴近实机行为）：「打开插件安装器时，不打断我正在浏览的列表」；或「后台刷新时，不重置列表和滚动位置」。若必须保留「防止…自动刷新」句式，至少补全对象：「防止打开插件安装器时列表被刷新打断」。
  2. 词汇层面（建议统一，不与产品指定冲突）：**不要用「更新」指这件事**，与开关统一为「自动刷新」；顺便统一"插件管理器 → 插件安装器"（见 F9，页内说明自己用的就是「插件安装器」）；「自动重载」是开发词，正文改成「后台刷新」。
  3. 安抚句与恐惧同词：说明改为「后台刷新照常进行（**不会阻止联网，也不会阻止插件更新**），只是不再把列表和滚动位置重置。」
### F3 · P1 · 两个开关有隐藏耦合：关掉第 1 项后，第 2 项"开着但不生效"
- **现象**：帧 2 的标题明确写「第二项仍开」（HTML:66），页面视觉上把两项呈现为互相独立。但代码上，位置恢复的入口条件是 `config.ListScrollY is { } saved && saved > 1f`（`InstallerListScroll.cs:129`），而位置记录是**每帧**把当前滚动值写回配置（`:310-339`，条件只有 `RememberListScroll && hasContent`）。关掉第 1 项后，后台重载会照常把列表顶回顶部 / 重建列表子窗口（正是用户刚选择接受的行为），列表重建后滚动值为 0、内容仍在（`max > 0` → `hasContent` 成立），于是 `ListScrollY` 被改写为 0；下次打开时 `saved > 1f` 不成立 → 不恢复 → 从顶部开始。
- **影响**：出现最难排查的一类状态——**勾选着的开关时好时坏**（两次打断之间没发生重载就恰好能恢复）。用户无法归因，只会认为"这个功能不靠谱"。同时页面对这层依赖**一字未提**。
- **最小改法**（建议，按代价从低到高）：
  1. 第 2 项下加依赖行：「需要上面那项也开着，否则后台刷新会把记住的位置清零」；
  2. 关掉第 1 项时，把第 2 项的说明换成告警色的一句话，或给第 2 行加"（位置可能被后台刷新重置）"后缀；
  3. 关掉第 1 项时把第 2 项置灰（ImGui `BeginDisabled`）并给出原因——但会让用户失去"只要跨会话记忆"的选择，需产品确认。
- **证据等级**：代码路径推理（非实测）；上一轮评审已把它列为待验证假设（`docs/hci/review-2026-09-17-installer-tab-heuristic.md:114`）。验证步骤见 Open questions Q1。
### F4 · P2 · 缺「什么时候会被打断」和「想立刻看最新列表怎么办」
- **现象**：开关把触发点说成"**打开**插件安装器（时）"，正文只说"别再自己刷新"；页面没有任何一处说明打断的真实来源（其他插件在后台周期性重载仓库）与发生时机（浏览过程中、约每十几分钟一次）。关闭后的可见后果也没有一句（连"关掉后列表会被顶回顶部"都没写）。
- **影响**：用户无法把"我也遇到过列表突然跳回顶部"与这一页联系起来，也就无法判断值不值得开；默认开的情况下，他既说不清好处，也说不清关掉的代价——**"我该不该开"在本页无解**。另外，"想马上看到最新上架的插件怎么办"无出口（手动刷新/重开安装器是否仍然生效，页面未承诺）。
- **最小改法**（建议）：正文补一句场景与副作用，例如「其他插件每隔几分钟会在后台重载仓库，那一刻列表会闪一下「正在加载插件…」并被顶回顶部。」＋「关掉后就会恢复这种打断；手动点刷新、重开安装器不受影响。」
### F5 · P2 · 效果天然不可见，页面又不给任何"已生效"信号
- **现象**：两项的效果都是"什么都没发生"（不被打断、位置被恢复），页面只有勾选框本身表示状态；实现里也没有该页的状态区/计数（`InstallerTab.cs:15-37` 全部内容就是一句正文 + 两个开关 + 两行说明）。
- **影响**：用户无法自证功能在跑（尤其当它因为 F3、或因为卫月升级导致自动停用时，界面完全一样）。这属于典型的"系统状态不可见"，也是"我该不该相信这个开关"的摩擦来源。
- **最小改法**（建议）：在说明行尾追加一行灰字状态，例如「本次会话已拦下 3 次自动刷新（最近 13:13）」/「未生效：…」，把"看不见的效果"变成一行可核对的数字。
### F6 · P2 · 三处文案说同一件事，把预算花在了不需要解释的地方
- **现象**：正文一句话同时概括两项效果（`InstallerTab.cs:17`），第 1 项的说明重复"不再顶回顶部"（`:26`），第 2 项的说明重复"下次打开接着看"（`:36` vs 标签里已经写了"（下次打开接着看）"）。同一信息出现 3 次。
- **影响**：重复本身不致命，但它占掉了承载 F3（依赖）与 F4（时机/关闭后果）的空间；读者还会因为"说了三遍"而误以为"这功能很重要但也就这点内容"。
- **最小改法**（建议）：只保留一处结果描述（说明行），把正文腾给"什么时候会发生 + 关掉会怎样"；标签里去掉与说明重复的括注。
### F7 · P2 · 页签/副标题只覆盖一半功能，「记住看到哪里」没有入口
- **现象**：副标题列的三项能力是「汉化 / 体检 / 拦住自动更新」（`MainWindow.cs:48`），页签也是「拦住自动更新」（`:69`），但页内有两个开关，第二个（记住位置）既不在副标题里，也不在页签名里。作者自己在工程描述里是用括号补上的：`拦住插件安装器自动刷新（含记住列表浏览位置）`（`FireGaze.csproj:17`），UI 里没有这个括号。
- **影响**：想找"为什么每次打开安装器都跳回顶部"的用户，按功能清单找不到对应入口；页签名会让人以为这一页只管"拦"，看到第二个开关时反而怀疑自己是不是点错了页。
- **最小改法**（建议，页签名可能受产品指定约束）：副标题补上第四项（「记住浏览位置」），或页内加一行小节说明；若允许改名，页签用覆盖两者的词（如「列表不被打断」「安装器增强」）。
### F8 · P2 · 还原图与实机布局不一致（会影响基于它做的后续判断）
- **现象**（HTML 与实现逐条对比）：
  - 说明文字缩进 22px（HTML:38 `.indent`），实现里两条说明是 `ImGui.TextDisabled` 直接绘制、**没有** `ImGui.Indent`（`InstallerTab.cs:26,36`）→ 实机是左对齐到勾选框，不是对齐到标签文字。mockup 让人以为存在从属层级。
  - 勾选态画成浅色**填充方块**（HTML:34-35 `.check.on::after`），ImGui `Checkbox` 实际是 ✓ 勾形。状态可辨识度被 mockup 改写了（并未改变上述结论，但会误导"勾选态够不够醒目"的判断）。
  - 品牌行 + 副标题被画成一条深色**标题栏色带**并加粗（HTML:24-25），实机是内容区第一行：强调色 `FireGaze` + `SameLine()` 的灰字副标题 + `Separator()`（`MainWindow.cs:45-49`）。层级观感不同。
  - 窗口画成 700×420（HTML:22），而实机默认 700×620、最小高 440（`MainWindow.cs:31-34`）→ 该 mockup 的尺寸在实机不可能出现，页内留白比例不代表实际。
  - 可读性：12px 的 `#909090` 副标题压在 `#2b2b2b` 上，按 CSS 值估算对比度约 4.4:1，略低于常规文本 4.5:1（HTML:11,24-25）。属边缘项，仅记录。
- **影响**：这一页的结论（F1–F7）不受影响，但若后续按 mockup 讨论"缩进层级/勾选态醒目度/首屏密度"，会基于不存在的布局讨论。
- **最小改法**（建议）：mockup 去掉 `.indent`（或把实现补上 `ImGui.Indent`，两者只能选一）；勾选态改画 ✓；品牌+副标题移回内容区；窗口改成 700×620（并标注 560×440 的最小态另画一帧）。
### F9 · P2 · 跨产物名称与承诺不一致（同一功能在仓库里至少有四套说法）
- **现象**：页签/副标题「拦住自动更新」（`MainWindow.cs:48,69`）；工程描述「拦住插件安装器自动刷新」（`FireGaze.csproj:17`）；README「浏览插件仓库阻止自动**重载**」（`README.md:19`）；**已发布**的 `pluginmaster.json`（AssemblyVersion 1.0.0.23）描述里这项功能**完全没提**，只剩"汉化 + 坏链检测"，用户点进插件前看不到这项能力；汉化词表里的市场文案又叫「列表自动刷新拦截」，并写着「手动刷新与**打开安装器不受影响**」——这与开关名「防止**打开**插件管理器自动刷新」字面冲突（`translations.json:21774-21779`）。
- **影响**：用户在"安装器里读到的介绍 → 装完后看到的页签 → 页内开关"这条路径上要重新学三次同一件事；且"打开安装器不受影响"与"防止打开…自动刷新"互相打脸，正是 F2 那种"看不懂到底拦不拦"的外部放大器。
- **最小改法**（建议）：把这项功能在 README / pluginmaster 描述 / 词表市场文案 / 页签 / 开关里的**动作描述收敛成同一句**，并统一使用「自动刷新」一个词；pluginmaster 是唯一用户看不到 UI 前会读到的文本，必须补上这句。
### 已核对、无需修改（避免误报）
- 帧 1 标注「默认态（两项都开）」与实现默认值一致（`Configuration.cs:58,64` 均为 `true`）。
- 还原图文本与实现字符串**逐字一致**（HTML:50/53/54/58/59 ↔ `InstallerTab.cs:17/21/26/31/36`），副标题与页签也逐字一致（`MainWindow.cs:48,69`）→ 文本层还原度可信，本文所有文案结论都成立。
- 副标题第三项与页签同名（「拦住自动更新」）这一点是**一致**的，不一致发生在"页签/副标题 ↔ 开关/正文"之间（见 F2、F7），不要把两者混为一条。
- 说明行的灰字 `TextDisabled` 在 `#191919` 上的实际对比度约 5.5:1，**达标**，不构成可读性问题（仅 12px 副标题是边缘项，已并入 F8）。

- 命名与承诺的四处差异：`FireGaze.csproj:17`、`README.md:19`、`pluginmaster.json`、`translations.json:21774-21779`。
**推断（有代码/文档依据，需实测确认）**
- F3「关掉第 1 项后第 2 项失效」：由上述代码路径推导；上一轮评审也把它列为待验证项（`docs/hci/review-2026-09-17-installer-tab-heuristic.md:114`），**本次未运行游戏，未实测**。
- 「玩家会把『拦住自动更新』读成阻止插件更新/阻止联网」：基于词义与语境的风险预测，**无用户数据支撑**（技能明确禁止把假设当证据）。
- F9 中"词表市场文案是用户会看到的文本"：`translations.json` 是插件的汉化词表，该条目内容为 FireGaze 自身条目（`FireGaze` 键，`:21766` 起），是否会被渲染到用户可见位置取决于卫月读取该词表的路径，**未在本仓库内验证**。
**假设（无证据，需要时就地确认）**
- 目标用户不读源码、不查文档，只凭这一页做决定；本页主要任务是"确认在拦什么 + 决定开关"。
- 产品方指定「防止打开插件管理器自动刷新」这行**不可改词**，因此相关建议均按"若可改用 X，若不可改则至少补 Y"给出，不视为错误。
- mockup 的 CSS 配色与实机 ImGui 主题无系统性偏差（若偏差较大，F8 的对比度子项需重算）。
## Open questions
1. **Q1（验证 F3，最关键）**：实机把第 1 项**不勾选**、第 2 项勾选 → 打开插件安装器滚动到中段 → 等一次后台重载（或触发重载）→ 关掉安装器再打开。位置是否恢复？预期**不恢复**（且日志/配置里 `ListScrollY` 已被清零）。再勾上第 1 项复测同一步作对照。
2. **Q2（被隐藏的后果）**：拦下一次刷新期间，安装器列表里**新上架/新更新的插件**会立刻出现吗？若不会，必须在页面写清"想立刻看到最新列表就点手动刷新/重开"，否则这是真正的隐藏后果。
3. **Q3**：掩蔽刷新过程中，安装器自带的"检查更新/刷新"按钮、加载态提示是否仍然正常工作？页面要不要像市场文案那样承诺"手动刷新不受影响"？
4. **Q4**：产品方对页签/副标题的改动权限边界在哪？允许把副标题扩展到四项、或把页签改成覆盖两个功能的词吗？这决定 F7 的解法。
5. **Q5**：关闭第 1 项后，用户是否仍然想要"仅跨会话记忆位置"？（决定 F3 是加依赖说明、还是置灰第 2 项。）
